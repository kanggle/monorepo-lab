## Context

### 무엇을 원하나

팬플랫폼에서 아티스트 굿즈를 살 수 있게 한다. 소유자 대화(2026-09-29)에서 세 갈래를 비교했다:
A 팬플랫폼 안에 디지털 굿즈 · B 팬플랫폼 안에 실물 굿즈(이커머스 재구현) · **C 이커머스 스토어로 연결**.
소유자가 **C** 를 골랐다. 근거는 업계 표준 구조 — 커뮤니티 앱과 쇼핑몰을 **별도 서비스**로 두고
**계정만 통합**(예: 커뮤니티 ↔ 샵) — 와 같고, 이 저장소에는 이미 그 두 조각이 있다는 것이다.

## Decision

D1~D4 는 갈래와 무관하게 고정이다. **D5 만 소유자가 고른다.**

### D1 — 굿즈는 **이커머스의 상품**이다. 팬플랫폼은 데이터·주문·결제를 하나도 갖지 않는다

- 굿즈 = `product-service` 의 일반 상품(실물). 주문·결제·배송은 스토어의 기존 흐름을 그대로 탄다.
- 팬플랫폼이 더하는 것은 **바깥으로 나가는 링크**뿐이다. 새 백엔드 호출 0, 새 서비스 0.
  갈래 D 는 그 링크를 **카드로** 그리려고 스토어의 **공개 번들 저장본을 읽기만** 한다 — 이것도 백엔드 호출이 아니다.
- 🔵 그래서 팬 웹의 **«익명 방문 = 게이트웨이 호출 0»** 불변식(`widgets/header/Header.tsx` 머리 주석)이 그대로 산다.

### D2 — 굿즈 시드는 **기존 세 곳 + 픽스처**로 들어간다 (새 경로 없음)

- postgres `db/migration/V20__seed_artist_goods.sql` · h2 `db/migration-h2/V13__seed_artist_goods.sql`
  · `infra/demo/public-data/fixtures/raw-backend-responses.mjs` → 생성기로 `snapshots/store.json`.
- 🔴 `store.json` 은 손으로 쓰지 않는다(`infra/demo/public-data/README.md` § 시드는 생성한다).
- 🔴 postgres 시드는 `tenant_id` 를 **변형 행까지** 채운다 — `TASK-MONO-638` 의 `V19` 결함(변형 `tenant_id` 누락)을 되풀이하지 않는다.
- 🔴 새 마이그레이션이다. 적용된 `V8`/`V19` 를 **고치지 않는다**(Flyway 체크섬 — 기존 볼륨이 기동에서 죽는다).

### D3 — 스토어 주소는 **환경변수 하나**, 기본값은 정본 공개 호스트

- 팬 웹 `NEXT_PUBLIC_STORE_URL`, 미설정이면 `https://store.hubwang.com`.
- 🔵 기본값이 운영 주소인 이유: 이 값을 안 넘긴 환경(Vercel 미설정·compose 누락)에서 **조용히 죽는 쪽이
  아니라 운영 스토어로 가는 쪽**으로 실패하게 한다. `.local`/`sslip.io` 는 기본값이 될 수 없다
  (`check-client-graph-backend-origins.mjs` 가 막는 부류이고, 방문자 브라우저에서 안 열린다).

### D4 — 링크는 **평범한 `<a>`**, 서버 컴포넌트 안에서

- `'use client'` 를 새로 만들지 않는다. 헤더와 아티스트 프로필은 서버 컴포넌트로 남는다.
- 외부 사이트로 나간다는 것을 **글자로** 표시한다(예: 「굿즈샵 ↗」).

### D5 — 팬 화면이 스토어의 **무엇을** 가리키는가 — 🔴 **소유자 결정**

| 갈래 | 스토어 데이터 | 헤더 「굿즈샵」 | 아티스트 페이지 「공식 굿즈」 | 팬 코드가 아는 스토어 식별자 |
|---|---|---|---|---|
| **A** 아티스트별 카테고리 | 아티스트마다 카테고리 1개(6개) | 🔴 «굿즈 전체» 를 가리킬 수 없다 — 필터가 정확 일치라 상위 카테고리는 0건. 스토어 첫 목록(`/products`)으로 | `/products?categoryId=<그 아티스트 카테고리>` | **아티스트 6명 × 카테고리 id** 대응표 |
| **B** 굿즈 카테고리 1개 + 예명 검색 | 카테고리 「아티스트 굿즈」 1개 | `/products?categoryId=<굿즈>` | `/products?categoryId=<굿즈>&q=<예명>` | **카테고리 id 1개** (+ 이미 가진 예명) |
| **C** 헤더 링크만 | 카테고리 「아티스트 굿즈」 1개 | `/products?categoryId=<굿즈>` | 없음 | **카테고리 id 1개** |
| **D** 굿즈 카드 → 상품 상세 | 카테고리 「아티스트 굿즈」 1개 | `/products?categoryId=<굿즈>` | 그 아티스트 굿즈 **카드**(사진·이름·가격) → `/products/<상품 id>`, 「전체 보기」 → B 와 같은 목록 | **카테고리 id 1개** — 상품 id 는 코드에 **안 적는다**(저장본에서 읽는다) |

- **A** 의 대가: 두 프로젝트의 id 가 **6쌍** 묶인다. 아티스트를 추가하면 두 저장소 위치를 같이 고쳐야 하고, 한쪽만 고치면 링크가 **0건 목록**으로 조용히 떨어진다. 스토어 카테고리 드롭다운이 6 → 12칸.
- **B** 의 대가: 예명이 굿즈 상품 **이름에 들어 있어야** 검색에 걸린다(시드 규약으로 지킨다). 예명이 바뀌면 링크가 0건이 된다 — A 와 같은 부류지만 묶인 값이 id 가 아니라 **사람이 읽는 이름**이다.
- **C** 의 대가: 아티스트 페이지에서 바로 그 아티스트 굿즈로 못 간다. 코드는 가장 작다.
- **D** 의 대가: 팬 웹이 **스토어의 공개 데이터 형식**(`@demo/public-data` 의 `PublicProduct`)에 의존한다. 아티스트 ↔ 굿즈의
  짝은 B 와 같은 규약(굿즈 카테고리 + 이름이 `<예명> ` 으로 시작, R4)으로 저장본에서 **걸러 낸다**. 팬 코드가 늘어난다(카드 + 시험).
  - 🔵 실측(2026-09-29) — 결합이 생각보다 작은 이유: ① 팬 웹은 **이미 같은 패키지**에서 `fan.json` 을 읽는다
    (`features/public-browse/api/read.ts:8`), 패키지는 `./snapshots/*` 를 내보낸다. ② 팬·스토어 Vercel 빌드 규칙이
    **둘 다** `infra/demo/public-data` 를 감시한다(`fan-platform-web/vercel-ignore.sh` · `web-store/vercel-ignore.sh`) ⇒
    상품 데이터가 바뀌는 커밋은 두 사이트를 **같이** 다시 배포한다. «팬 카드가 스토어에 없는 상품을 가리킨다» 는
    **한쪽만 배포될 때** 생기는데, 그 모양이 구조적으로 막혀 있다.
  - 🔴 남는 위험: 스토어가 Blob 저장본으로 전환하면(`DEMO_PUBLIC_DATA_BASE_URL` 설정) 스토어는 발행본을, 팬은 번들을 읽게 된다
    — 그때는 두 사이트가 **다른 세대**를 볼 수 있다. 오늘은 미설정이다(`TASK-MONO-678`).

## Consequences

### ACCEPT 가 인가하는 것

`TASK-MONO-739` 의 구현 — 시드 세 곳 + 픽스처 + 생성된 `store.json` + 팬 웹의 링크(D5 갈래대로) + `NEXT_PUBLIC_STORE_URL`.

### 건드리지 않는 것

- 스토어의 주문·결제·배송 코드, 팬의 멤버십·결제 코드.
- 두 사이트의 로그인·테넌트 해석(`ADR-MONO-072` 가 정한 그대로).

### 새로 생기는 위험

- 🔴 **실 백엔드 데모에는 재굽기 전까지 굿즈가 없다.** 공개 열람은 번들 저장본이라 즉시 보이지만, 로그인 후
  주문 경로는 `product-service` DB 를 쓴다 — 새 마이그레이션은 데모 서버 이미지를 다시 구워야 들어간다.
  그 전에는 「공개 목록엔 있는데 장바구니에 담으면 없는 상품」이 된다.
- 🔴🔴 **팬에서 로그인한 채 스토어로 넘어가면 스토어 로그인이 거절된다.** `ADR-MONO-072` 의 라이브 실측
  (`TASK-MONO-633` 패스 A′ «팬 → 스토어») 결과는 `/login?error=account_type_mismatch` 이고 IdP 폼을 거치지 않는다 —
  SSO 세션이 팬 테넌트 계정을 들고 있어 스토어의 consumer 가드가 거부한다. 세션이 남아 있는 한 다시 시도해도 같다.
  공개 열람(로그인 없이 굿즈 보기·상세)은 영향이 없고, **구매(로그인)** 단계에서 방문자가 밟는다.
  - 고치는 것은 072 가 «갈래로 남긴» ⓐ(클라이언트별 테넌트 재해석)이고 인증 모델 변경이라 **072 를 다시 여는 결정**이다.
    이 연결이 072 가 적은 «프로덕션 요구» 의 첫 사례다.
  - 🔴 ⓐ 만으로도 부족하다: 계정은 **가입한 테넌트 안에** 생기므로(`web-store/src/app/(auth)/signup/page.tsx` 머리 주석),
