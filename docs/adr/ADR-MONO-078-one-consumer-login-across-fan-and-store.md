## Context

### 무엇을 원하나

팬에서 로그인한 사람이 스토어로 넘어가도 **로그인된 상태**여야 한다. 팬에서만 가입한 사람도 스토어를 쓸 수 있어야 한다.
소유자는 업계 방식 셋(① 테넌트 분리 유지 · ② 계정 연결 · ③ 전역 소비자 계정) 중 **③** 을 골랐다(2026-09-29).

### 지금 어떻게 동작하나 (실측 — 코드, 2026-09-29)

| 상황 | 동작 | 근거 |
|---|---|---|
| 팬 세션 → 스토어, 스토어 계정 **있음** | IdP 로그인 폼이 **다시** 뜬다. 비밀번호 재입력 | `AuthorizeSessionTenantGate` (`TASK-BE-605`, 2026-09-26) |
| 팬 세션 → 스토어, **팬에서만 가입** | 폼에서 로그인 실패 `CREDENTIALS_INVALID`(일반 문구). 막다른 길 | `CredentialAuthenticationProvider.resolveCredential` — 소비자 client 는 자기 테넌트만 찾는다(`TASK-BE-604`) |
| 스토어 로그인 후 팬으로 | 다시 로그인. IdP 세션은 **한 principal** 만 담는다 | `multi-tenancy.md` § SSO |

🔴 `ADR-MONO-072`(09-11) 의 «`account_type_mismatch` 로 거절» 은 BE-605 **이전** 측정이다. 코드는 그 뒤 바뀌었다
(라이브 데모는 재굽기 전이면 여전히 옛 동작일 수 있다 — 서버를 띄우지 않고는 못 잰다).

### 왜 그런가 — 계정이 **테넌트마다 따로**다

| 층 | 무엇이 테넌트별인가 |
|---|---|
| IAM | `accounts` UNIQUE `(tenant_id,email)` · `credentials` UNIQUE `(tenant_id,email)`, 계정과 1:1 · `identities` UNIQUE `(tenant_id, primary_email)` · `account_roles(tenant_id, account_id, role)` · `social_identities` UNIQUE `(tenant_id, provider, provider_user_id)` |
| 토큰 | `sub` = 테넌트 한 곳의 계정 UUID · `tenant_id` = **단일값**(«두 번째 테넌트 클레임은 없다», `jwt-standard-claims.md`) |
| 팬 | 게이트웨이 + 서비스 4개가 `tenant_id = fan-platform` 을 요구(5곳). `sub` 를 저장하는 컬럼 **11개 / 테이블 10개** |
| 이커머스 | 게이트웨이가 `ecommerce` 요구, 하위 서비스는 `X-Tenant-Id`·`X-User-Id` 헤더로 저장·필터. 사용자 id 테이블 **약 11개** |
| 시험·시드 | `demo@demo.com` 은 테넌트별 **세 행**(ecommerce·fan-platform·iam). 테넌트 id 를 인증 맥락에 쓰는 시험 파일 약 **68(fan) + 44(ecommerce)** |

🔴 «사람» 단위 id 는 **없다**. `ADR-MONO-040` D4 는 `identity_id` 를 «cross-platform linkage key» 라 부르지만
스키마가 `(tenant_id, primary_email)` 로 묶어 테넌트를 넘지 못한다.

### 🔵 계약은 이미 전역 로그인을 약속한다

`platform/contracts/jwt-standard-claims.md` § Single Sign-On (SSO) Scope:

> *"An identity may request an access token for **any platform on which it holds ≥ 1 role** … without re-entering credentials."*

지금 모델(사람 = 테넌트별 계정 여럿)에서는 그 문장의 «identity» 가 테넌트를 넘지 못해 **소비자 둘 사이에서 참이 아니다.**
이 ADR 은 계약을 새로 쓰는 게 아니라 **계약을 참으로 만드는** 결정이다.

## Decision

D1~D4 는 갈래와 무관하게 고정이다. **D5 만 소유자가 고른다.**

### D1 — 범위는 **소비자 둘**(fan-platform · ecommerce). 콘솔(`iam`, 운영자)은 **밖**이다

- 운영자 계정은 자동으로 만들어지지 않는다. 콘솔의 SSO 규칙(`TASK-BE-610`)은 그대로다.
- 다른 테넌트(wms·scm·erp·finance)는 소비자가 아니라 이 결정과 무관하다.

### D2 — 🔴 **기존 계정은 이메일로 조용히 합치지 않는다** (`ADR-MONO-034` § 1.3 을 그대로 따른다)

- IAM 은 **이메일 인증을 로그인 조건으로 쓰지 않는다**(실측: `CredentialAuthenticationProvider` 에 참조 0). 같은 이메일이라는
  사실만으로 합치면, 남의 이메일로 팬에 가입한 사람이 그 사람의 **스토어 계정에 비밀번호 없이** 들어간다.
- 이미 팬·스토어에 따로 계정이 있는 사람은 **본인 확인을 한 번** 거쳐 묶는다 — 로그인한 계정 말고 다른 쪽 계정의 비밀번호를 한 번 입력한다.
  (묶기 전에는 지금처럼 동작한다 — 나빠지는 사람은 없다.)
- 새로 가입하는 사람은 **처음부터 전역 계정**으로 태어난다.

### D3 — 사이트 **첫 방문**은 «이용 동의» 한 화면이다 (가입 폼이 아니다)

- 전역 계정으로 로그인한 사람이 처음 가는 소비자 사이트에서는 그 사이트 이용 동의 화면을 **한 번** 본다. 비밀번호도, 가입 폼도 없다.
- 그래서 «팬에서만 가입해 스토어 계정이 없는 사람» 이 **사라진다** — 소유자가 고른 ①(가입 안내)은 이 화면으로 대체된다.
- 동의 여부는 사이트별로 기록한다. 약관 본문은 지금 저장소에 없다(실측: IAM 에 약관 모델 0, 팬 로그인 화면의 안내 문구 링크가 `href="#"`) — 문구는 데모용이다.

### D4 — 소셜 로그인도 같은 규칙을 탄다

`social_identities` 는 지금 테넌트별이다. 전역 계정 아래에서는 **사람 단위**로 묶이고, 기존 소셜 신원은 D2 처럼 본인 확인으로만 묶는다
(`multi-tenancy.md:373` 의 «기존 교차 테넌트 소셜 신원은 옮기지 않는다» 소유자 결정을 뒤집지 않는다).

### D5 — 전역 계정의 **모양** — 🔴 **소유자 결정**

🔴 **이 표는 2026-09-29 개정판이다.** 첫 판의 A(«소비자 테넌트 하나로 통합», `tenant_id=consumer`)는 설계 결함이 드러나
§ Alternatives 로 옮겼다 — 아래 A 는 그 자리를 대신한 «업계 정석을 제대로 옮긴» 안이다(대화에서는 «A′» 로 불렸다).

| | **A. 소비자 계정 풀 하나 + 토큰 테넌트는 사이트 기준** | **B. 전역 로그인 + 사이트별 계정** |
|---|---|---|
| 한 줄 | 소비자는 **사람당 계정 하나**. 팬·스토어는 그 계정을 쓰는 **클라이언트**다. 토큰의 `tenant_id` 는 지금처럼 **들어간 사이트의 테넌트** | 로그인은 **사람 단위 계정 하나**. 각 사이트에는 그 사람에 **묶인 사이트 계정**이 있고, 첫 방문 동의 때 만든다 |
| 사이트가 보는 사용자 id(`sub`) | **두 사이트에서 같다** — 업계 정석(한 회사의 자기 서비스끼리 같은 id) | **사이트마다 다르다**(외부 앱에 로그인을 제공할 때 쓰는 pairwise 모양) |
| 토큰의 `tenant_id` | 지금처럼 `fan-platform` / `ecommerce` — `ADR-MONO-072` 가 «ⓐ» 로 남긴 «같은 `sub` 가 클라이언트별로 다른 `tenant_id`» | 지금처럼 |
| 바뀌는 곳 | **IAM**: 소비자 계정·자격을 테넌트 밖(풀)으로 · authorize 때 client 테넌트로 토큰 발급 · 사이트별 역할·동의 기록 · `AuthorizeSessionTenantGate` 가 같은 사람이면 재인증 대신 통과. 팬·이커머스 **테넌트 검사·데이터의 테넌트 값 변경 0** | **IAM 만**: 사람 계정·로그인 자격 · 사이트 계정 ↔ 사람 연결 · 없으면 동의 → 생성(`SocialSignupUseCase` 선례) · 게이트가 같은 사람이면 **principal 전환**. 팬·이커머스 **변경 0** |
| 🔴 대가 | **기존 계정을 묶을 때 id 가 하나로 줄어든다** — 사라지는 쪽 id 로 저장된 팬·스토어 행(팬 11 컬럼, 이커머스 약 11 테이블)과 운영자 매핑(`ADR-MONO-044` D5 — 운영자 권한이 소비자 계정에 붙는다)을 살아남는 id 로 옮겨야 한다. 새 가입자는 처음부터 id 하나라 이전이 없다 | 두 사이트의 id 가 달라 «같은 사람» 을 알려면 IAM 에 물어야 한다. 정석이 아니다(자기 사이트에 외부 앱용 방식을 쓴다) |
| 계약 | `sub` 가 «사람의 id» 가 된다 — 계약 문장(«globally unique, immutable across all platforms») 과 **처음으로 일치**한다. `tenant_id` 의미는 그대로 | `sub`·`tenant_id` 의미 그대로 |
| 콘솔 | 운영자 모델·테넌트 전환 **그대로**. ① 묶인 계정의 운영자 매핑 이전(위 대가) ② 콘솔 로그인의 이메일 교차 조회: 지금은 같은 이메일이 팬·스토어에 둘 다 있으면 `LOGIN_TENANT_AMBIGUOUS` 로 막히는데 계정이 하나가 되면 풀린다 — 행동 변경이라 시험으로 고정 | 그대로 |
| 예상 규모 | 10~14개 태스크, IAM 중심 + 묶기 시 id 이전 | 8~12개 태스크, IAM 중심 |

## 추천 — 🔴 **구현자의 선호**다. 소유자 결정이 아니다

**A.** 한 회사의 자기 서비스끼리 사용자 id 를 공유하는 것이 업계 정석이고, 계약 문장(`sub` = 모든 플랫폼에서 같은 계정 id)과도
처음으로 맞는다. 첫 판에서 B 를 추천한 근거는 «반경» 이었는데, 그 반경의 대부분(테넌트 값 이전·테넌트 검사 수정)은 **결함 있는
첫 판 A 의 것**이었다 — 개정된 A 는 테넌트를 건드리지 않아 B 와 반경이 비슷하고, 추가 비용은 기존 계정 묶기의 id 이전뿐이다.

🔴 첫 판의 추천(B)은 이 개정으로 **철회**됐다 — 소유자가 본 적이 있으니 기록으로 남긴다(§ History).

## Alternatives Considered

- **① 테넌트 분리 유지(현재)** — 표준적이고 안전하지만 요구(로그인 유지)를 안 채운다. 소유자가 고르지 않았다.
- **② 계정 연결만(전역 계정 없이)** — B 의 «기존 계정 묶기» 와 같은 장치지만, 새 가입자도 사이트마다 따로 태어난다. «팬에서만 가입한 사람» 이 남는다.
- **같은 이메일이면 자동 병합** — 🔴 기각. `ADR-MONO-034` § 1.3 의 권한 상승 경로 그대로다(D2).
- **소비자 테넌트 하나로 통합(첫 판의 A — 토큰 `tenant_id=consumer`)** — 🔴 **기각(설계 결함)**. 이커머스의 `tenant_id` 는 «사이트» 가 아니라
  **스토어를 운영하는 회사**다(멀티셀러 마켓플레이스, `ADR-MONO-030`). 쇼핑객 토큰의 테넌트는 그 스토어 회사와 같아야 주문·상품 행과 맞물리고
  (카탈로그부터 `tenant_id='ecommerce'`, 게이트웨이가 소비자 토큰의 테넌트를 그 값으로 못 박는다 — `docs/guides/interview-demo-walkthrough.md`),
  콘솔 운영자는 `ecommerce` 로 **테넌트를 전환해** 그 행을 본다(`DomainTenantGate.tsx` — `tenant=ecommerce → 주문 5 · 상품 24`, 콘솔 85 파일이
  `ecommerce`·`fan-platform` 을 테넌트 값으로 쓴다). 쇼핑객을 `consumer` 로 옮기면 그 연결이 끊기고, 다른 회사 스토어가 생겨도 자기 쇼핑객을 가르지 못한다.
  🔴 첫 판은 이 안의 대가를 «두 제품 데이터가 한 테넌트에 섞여 격리 시험이 두 제품을 못 가른다» 로 적었는데 그것은 **과장**이었다 — 팬·이커머스는
  서비스·DB 가 이미 따로다. 진짜 결함은 격리가 아니라 **스토어 테넌트 = 운영 회사** 라는 모델과의 충돌이다.

## Consequences

### ACCEPT 가 인가하는 것

`TASK-MONO-741` — 갈래대로 **단계 티켓을 기안**하는 것까지. 구현은 단계 티켓마다 따로 간다(HARDSTOP-09).

### 건드리지 않는 것

- 콘솔 로그인·운영자 모델(D1), 콘솔의 테넌트 전환. 소비자가 아닌 테넌트.
- 팬·이커머스의 테넌트 검사와 데이터의 테넌트 값(두 갈래 모두). B 라면 사용자 id 도.

### 무엇이 바뀌나 (갈래 공통)

- `projects/iam-platform/specs/features/multi-tenancy.md` 의 «테넌트마다 한 계정» 규칙과 SSO 절 — 소비자 둘에 대해 다시 쓴다.
- `docs/guides/interview-demo-walkthrough.md` § 0 — 로그인 순서 안내가 필요 없어진다.

## CORRECTION (2026-10-02 UTC) — 셀러 행의 전제가 틀렸다 · `TASK-MONO-745` 는 079 로 흡수

🔴 위 «소유자 후속 결정» 표의 첫 행(셀러를 풀에 포함 → `TASK-MONO-745`)은 **«셀러 계정 = 사람이 로그인하는 계정»** 이라는 설명 위에서 내려졌다. `TASK-MONO-745` 착수 때 코드를 재니 그 전제가 거짓이었다.

- 셀러 계정은 product-service 가 셀러 등록 때 만드는 **기계 계정**이다 — 이메일 `seller+<tenant>+<sellerId>@marketplace.local`, 무작위 비밀번호, 주석상 «비밀번호로 로그인하지 않는다»(`AccountServiceSellerProvisioner#sellerEmail` · `#generatePassword`).
- 셀러로 일하는 로그인 경로도 아직 없다 — 셀러 범위 헤더(`X-Seller-Scope`)는 «운영자 토큰의 셀러 범위 클레임이 아직 연결되지 않았다»(ecommerce `GatewayIdentityConfig` 주석, `ADR-MONO-030` Step 4).
- 데모 시드에 사람 이메일의 셀러 계정은 없다.

그래서 «셀러가 같은 계정으로 쇼핑한다» 는 **기계 계정을 풀로 옮겨서는 생기지 않는다** — 그 사람의 계정이 셀러에 연결되는 모델이 먼저다. 위 «발견»(저장 역할 `SELLER` 가 시드 `CUSTOMER` 를 대체) 은 코드 읽기로 맞지만, 그 역할을 가진 계정에 로그인하는 사람이 없으므로 지금 사용자 영향은 없다.

**소유자 결정 (2026-10-02 UTC, 이 대화)**: *«079로 합치기»* — `TASK-MONO-745` 는 구현 없이 닫고, «사람의 풀 계정을 셀러에 연결해 그 스토어 사이트 역할 `SELLER` 를 준다» 를 `ADR-MONO-079`(소속사·셀러·콘솔 팬 관리)의 셀러 모델에 넣는다. 기계 계정은 지금 자리에 둔다. 079 기안 티켓 = `TASK-MONO-747`.
