## Context

### 무엇을 원하나

고객사 직원 · 협력사 직원 · 셀프 온보딩 운영자도 **개인 풀 계정 하나**로 로그인하고, 그 계정에 **회사 권한이 붙는** 모델 — GitHub · Slack 의 «개인 계정 + 조직 소속» 모양. 같은 사람이 쇼핑·팬 이용과 회사 일을 계정 하나로 한다.
플랫폼 관리자(`iam` · 플랫폼 범위 `'*'` 운영자)는 이 모델 밖에 둔다.

`ADR-MONO-078` 이 이것을 자기 안에 넣지 않은 이유(같은 ADR § 소유자 후속 결정): 직원은 **운영자 권한 평면**(누가 어느 회사 테넌트에 운영자로 붙나)을 바꾸고, 그 전에 **이메일 소유 확인**과 **회사 보안 정책 강제**가 있어야 안전하다.

## Decision

D1 · D2 · D5 · D8 은 갈래와 무관하게 고정이다. 갈래는 **범위**(어느 단계까지 인가하나)에서 갈린다. D3 · D4 · D6 의 수단은 라이더(구현자 기본값)로 두고, **D7 은 정하지 않는다**.

### D1 — 🔴 플랫폼 관리자는 **분리를 유지한다** (AC-2)

- 소유자 원문(2026-10-01): *«플랫폼 관리자 빼고 전부 풀»*. 플랫폼 범위 운영자(`tenant_id = '*'`, `iam` 콘솔)는 풀 계정에 붙지 않고, 지금처럼 계정 확인 면제 규칙(`CreateOperatorUseCase.java:92-100`)과 자기 자격으로 남는다.
- 이유: 플랫폼 관리자는 **모든 테넌트**에 닿는다. 그 신원이 개인 쇼핑 계정과 같으면, 그 계정의 약한 고리(비밀번호 재사용 · 소셜 로그인 · 인증 안 된 이메일)가 전 테넌트의 약한 고리가 된다.
- 🔴 **분리 ≠ 2단계 인증 면제.** 위 실측대로 플랫폼 관리자도 지금 주 경로에서 2FA 가 안 걸린다. D4 의 단계는 플랫폼 관리자에게도 적용된다(분리는 «풀에 안 붙는다» 만 뜻한다).

### D2 — 단계 순서는 **이메일 인증 게이트 → 2단계 인증 → 운영자 규칙 변경** 이고, 뒤 단계는 앞 단계 없이 나가지 않는다

- 운영자 규칙(D6)을 먼저 바꾸면 위험 ① 이 그대로 열린다(티켓 Failure Scenario 1) — 남의 이메일로 가입한 풀 계정이 회사 운영자 초대를 받는다.
- 단계마다 티켓 하나. 단계 3 티켓의 AC-0 은 «단계 1 · 2 가 `done/`» 이다.

### D3 — 위험 ①: **회사 권한이 붙는 순간에 인증된 이메일을 요구한다**

- 무는 자리: 풀 계정에 운영자 측면(회사 테넌트 운영자 · 협력사 참여자)이 **붙는 쓰기** 전부. 로그인 자체에는 걸지 않는다(소비자 이용은 지금 그대로 — 나빠지는 사람 없음).
- 🔴 **선행 조건 — 메일이 실제로 나가야 한다.** 지금은 어떤 환경에서도 인증 메일이 안 나간다(위 실측). 단계 1 은 «게이트» 이전에 **발송 어댑터**(prod 프로필)와 데모용 수신 경로를 포함한다. 그것 없이 게이트만 켜면 **아무도 회사 권한을 못 받는다**(게이트는 옳은데 길이 없는 상태).
- 🔴 `ADR-MONO-079` D5 셀러 구성원 수락이 같은 게이트를 받는가는 라이더 R1 이다(그 ADR 의 결정을 이 ADR 이 바꾸는 것이므로 소유자가 볼 수 있게 따로 적는다).

### D4 — 위험 ②: **IAM 로그인에 2단계 인증을 두고, 회사 테넌트 진입에서 그 사실을 본다**

- IAM(auth-service) 계정에 TOTP 등록 · 검증을 둔다(지금 admin-service 에만 있는 것을 계정 평면으로). 토큰에 «2단계를 거쳤다» 를 싣는다(표준 `amr` 클레임 — 계약 `jwt-standard-claims.md` 갱신이 단계 2 의 첫 일).
- 회사 테넌트 진입(assume-tenant, `ADR-MONO-020`) 및 운영자 토큰 교환이 그 클레임을 **회사 정책**과 비교한다 — 정책이 «2단계 필수» 인 테넌트는 없으면 거절.
- 🔴 지금의 `require_2fa`(역할 플래그)는 비상 경로에서만 문다. 단계 2 는 그것을 **주 경로(토큰 교환)에서도 물게** 하거나, 테넌트 정책으로 **대체**한다 — 둘 중 어느 쪽인가는 라이더 R2.
- 회사 SSO(외부 IdP 연동)는 이 ADR 의 범위 밖이다 — 2단계 인증으로 충분하지 않은 고객이 생길 때의 다음 결정으로 남긴다.

### D5 — 위험 ③: 묶음 회수는 **있는 장치를 그대로 쓰고**, 회수는 **측면만** 지운다 (계정은 안 잠근다)

- 그룹 · 배정 해제 · 파트너십 해지(위 실측)는 운영자 행 위에서 돈다 — 풀 계정에서도 그대로 끝난다. 새 장치를 만들지 않는다.
- 🔴 **퇴사 · 해지 = 운영자 측면 회수**이고 **풀 계정 잠금이 아니다.** 잠그면 그 사람의 쇼핑 · 팬 이용까지 막힌다 — `ADR-MONO-079` D5(셀러 정지 = 역할 회수, 계정 안 잠금)와 같은 원칙.
- 회사 소속의 기록 위치: `admin_operators.tenant_id`(회사 = 운영자의 홈 테넌트)와 파트너십 참여자 행. 계정의 `tenant_id` 는 `consumer-pool` 이므로 **회사 소속은 계정이 아니라 측면에만 있다**(티켓 Edge Case 1 의 답).
- 🔴 개인 메일로 초대된 직원은 퇴사해도 그 메일함을 잃지 않는다(티켓 Edge Case 2). 그래서 회수는 **메일 접근이 아니라 측면 회수**로만 일어나야 하고, «인증된 이메일» 은 **붙일 때의 증거**일 뿐 **유지 조건이 아니다**.

### D6 — 위험 ④: 운영자 규칙을 **«대상 테넌트 계정» 에서 «초대 → 인증된 본인 수락»** 으로 바꾼다 (갈래 A 에서만)

- `TASK-MONO-334` 의 «대상 테넌트에 가입 계정이 있어야» 를 대체: 운영자(회사 관리자)가 이메일로 초대 → 그 이메일을 **인증한** 풀 계정이 **로그인한 상태로** 수락 → 운영자 측면 생성. 이메일 일치만으로는 붙지 않는다(D3 · `ADR-MONO-034` § 1.3).
- 내부 프로비저닝(회사 테넌트에 사이트 계정을 만드는 길)은 **풀 계정 초대**로 바뀐다 — 새 사이트 계정을 만들지 않는다.
- 풀 세션의 콘솔 진입(`TASK-BE-615` D-5 의 «콘솔 토큰 없음»)과 셀프 온보딩(044 — 풀 계정의 `platform-console-web` 토큰)이 열린다 — 단, **운영자 측면이 있는** 풀 계정만.
- 지금 사이트 계정으로 남은 셀프 온보딩 운영자 · 그 이메일의 풀 가입 거절(`TASK-BE-614` AC-6)은 이 단계에서 풀로 옮기고 거절을 걷는다.

### D7 — 🔵 직원 마스터 ↔ IAM 계정 연결 — **선택지만 적는다. 이 ADR 은 정하지 않는다**

결재·위임처럼 «사람» 을 도메인 마스터(직원)로 부르는 곳이 로그인하는 계정과 이어지는 방법:

| 선택지 | 무엇 | 대가 |
|---|---|---|
| **E1 직원이 계정을 안다** | `employees.account_id`(NULL 허용) — 직원 마스터에 IAM 계정 id. 결재함 술어는 «승인자 직원의 `account_id` = 내 `sub`» 로 · 계약의 `approverId` = 직원 id 유지 · E3 를 코드로 지킨다 | 직원 마스터(erp)가 IAM id 를 들게 된다(교차 컨텍스트 참조 — FK 없음, 쓰기 때 검증). 연결을 **누가 쓰나**(인사 담당 · 본인 수락 · D6 초대 수락의 부산물)를 따로 정해야 한다 |
| **E2 결재가 `sub` → 직원을 푼다** | 직원 마스터는 그대로. 결재 서비스(또는 별도 연결 표)가 «계정 → 직원» 매핑을 갖고, 요청 때 `sub` 를 직원 id 로 바꿔 계약대로 비교 | 매핑의 집이 결재 쪽에 생긴다 — 다른 도메인(wms · scm)이 같은 문제를 만나면 매핑이 도메인마다 복제된다 |
| **E3 지금대로** | 계약은 직원 id, 코드는 계정 `sub` 를 쓰는 공존을 유지. 데모는 승인자에 `sub` 를 넣는 편법 + 콘솔 보정(`TASK-PC-FE-311`) | 계약 E3 · 자기결재 비교가 **다른 id 공간**인 채 남는다(위 실측). E3 를 누가 고치는 순간 데모 결재함이 0 이 된다 |

- 이 질문은 갈래(A/B/C)와 **독립**이다 — A 를 골라도 E1~E3 중 무엇인지는 따로 말해야 한다. 수락 문장에 직원 연결 letter 가 없으면 D7 은 **열린 채** 남고 기본값을 두지 않는다(§ 수락 형식).
- 🔵 E1 · E2 를 고르면 erp 의 다른 «사람» 칸(상신자 · 이력 처리자 · 위임 피위임자)도 같은 모델로 정리된다 — 지금은 위임 한 행에 두 id 공간이 섞여 있다(`seed-erp.sh:393`).

### D8 — AC-3: 078 이전 이중 계정은 **대상 없음**으로 닫는다 (측정 2026-10-07 UTC — 정적 0 · 라이브 ⚪)

- «인증 안 하고 묶지도 않은 사람이 남는다» 의 처리 선택지(남김 / 묶기 안내 강화 / 인증된 이메일끼리 자동 묶기)는 **물을 대상이 없다** — 결정하지 않고 보류한다(`ADR-MONO-078` § CORRECTION 2026-10-05 와 같은 성격).
- 되살리는 조건 = `TASK-MONO-743` 닫기 기록 «되살리는 조건»(078 이전 실사용자 데이터 유입 · 617 보다 먼저 소셜 키 배포) — 그때 같은 술어로 재고 이 절의 세 선택지부터 연다.
- 🔵 «인증된 이메일끼리 자동 묶기» 가 `ADR-MONO-078` D2 와 충돌하지 않는다는 티켓의 판단은 맞다(D2 의 근거가 «인증이 없어서» 였다) — 다만 D3 이 메일 발송을 들여오기 전에는 «인증된» 계정 자체가 생길 수 없다.

## 추천 — 🔴 **구현자의 선호**다. 소유자 결정이 아니다

**A.** 소유자가 말한 목표가 «플랫폼 관리자 빼고 전부 풀» 이고, A 만 그 상태에 닿는다. 단계 순서(D2)가 위험 ① 을 먼저 닫으므로 «규칙만 먼저 바뀌는» 실패는 구조적으로 막힌다.

B 를 가볍게 보지 않는다 — 단계 1 · 2 는 **풀 직원과 무관하게 지금 필요한 일**이다(079 D5 가 이미 미인증 이메일로 역할을 주고, 플랫폼 관리자도 주 경로에서 2FA 가 없다). 운영자 규칙 변경이 부담스러우면 B 로 구멍부터 닫는 것이 C 보다 낫다.

D7 에는 추천을 두지 않는다 — 착수 지시가 «선택지를 적되 정하지 말 것» 이었다.

## Alternatives Considered

- **직원은 계속 회사 테넌트 사이트 계정(현재)** — 표준적이고 격리가 단순하지만 소유자 목표(«전부 풀»)와 반대다. 같은 사람이 회사마다 · 소비자 사이트마다 계정을 따로 갖는다. 갈래 B · C 가 사실상 이 상태를 유지한다.
- **이메일 일치만으로 풀 계정에 회사 권한** — 🔴 기각. `ADR-MONO-034` § 1.3 의 권한 상승 경로 그대로이고, 위 실측대로 IAM 은 이메일 소유를 확인하지 않는다.
- **플랫폼 관리자도 풀로** — 🔴 기각(D1, 소유자 원문). 전 테넌트에 닿는 신원을 개인 계정의 약한 고리와 묶는다.
- **로그인 자체에 이메일 인증 필수** — 기각(지금 크기에서). 소비자 이용 전체를 메일 발송 경로에 묶는다 — 메일이 안 나가는 지금은 **모든 가입이 막힌다**. 권한이 붙는 순간에만 문다(D3).
- **2단계 인증 대신 회사 SSO 연동** — 보류(D4). 외부 IdP 연동은 고객이 요구할 때의 다음 결정이다.
- **시드에 «직원 id = 계정 id» 행을 넣어 결재 칸을 맞춘다** — 기각(소유자 결정 2026-10-07, `TASK-PC-FE-311`). 시드가 D7 을 몰래 정한다.

## 수락 형식

```
ADR-MONO-080 ACCEPTED — <A|B|C>
```

- 이름 · `ACCEPTED` · **갈래 letter** 세 요건이 모두 있어야 한다. 갈래 letter 만(«A 로»), 또는 «진행» 은 수락이 아니다 — 추천이 A 이므로 «A» 한 글자를 수락으로 읽으면 구현자 추천을 소유자 결정으로 읽는 귀속 오류와 구별되지 않는다(`ADR-MONO-079` § ACCEPT 게이트 기록).
- 선택 — 직원 연결: 같은 문장에 `· 직원연결 <E1|E2|E3>` 를 덧붙이면 D7 도 정해진다. **없으면 D7 은 열린 채 남는다**(기본값 없음).
- 선택 — 라이더 뒤집기: R1~R4 의 «뒤집기» 문구를 그대로 덧붙인다. 없으면 기본값이 구현자 선택으로 남는다(ACCEPT 시점 라이더 대조로 기록).
