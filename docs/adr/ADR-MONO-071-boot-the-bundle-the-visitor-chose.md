## Context — `TASK-MONO-477` 이 못 한 것

477 은 도메인별 기동을 만들었다. 그런데 실측하면 그 기능은 **부팅 뒤에만** 존재한다:

```
handler.py domain_start():
    state, _, _ = _state()
    if state != "running":
        return _resp({...,"message": "먼저 데모를 시작하세요 …"}, 409)
```

`/domain/start` 는 SSM RunShellScript 로 인스턴스에서 명령을 돌리므로 **인스턴스가 떠 있어야
한다.** 그래서 «켜기» 의 실제 순서는:

1. 방문자가 «팬 플랫폼만» 을 고르고 싶다
2. 그런데 인스턴스가 `stopped` → 도메인 선택은 **409**
3. 「데모 시작」을 눌러야 하고, 그 부팅은 systemd 유닛을 읽는다
4. `Environment=DEMO_PROFILE=full` ⇒ **8개 프로젝트 96 컨테이너**
5. 선택은 그 **뒤에야** 의미를 갖는다

⇒ *"프런트엔드 버튼만 나누고 내부적으로 전체 스택을 시작하는 구현은 금지한다"* 가 금지한
바로 그 상태이고, 그 상태가 **이미 존재했다.**

🔴🔴 그리고 이 결함은 **어떤 에러도 내지 않는다.** 96 컨테이너가 전부 정상적으로 뜬다 —
로그는 완벽하게 초록이고, 다른 점은 «방문자가 고른 것과 다르다» 뿐이다.

## Decision

### D1 — 선택을 **먼저 영속화하고, 그 다음에 켠다**

순서를 뒤집는 것이 이 결정의 전부다.

```
POST /bundle/start {"bundles":["fan"]}
  ① 선택을 SSM 파라미터에 저장   ← stopped 에서도 된다
  ② ec2.start_instances()
  ③ 부팅이 그 선택을 읽는다      ← demo-boot.sh selection
```

🔴 **왜 SSM 파라미터이고 인스턴스 안의 파일이 아닌가:** 쓰는 쪽(Lambda)과 읽는 쪽(인스턴스)이
**동시에 살아 있는 구간이 없다.** 방문자가 누르는 순간 인스턴스는 `stopped` 이므로 SSM
RunShellScript 로 파일을 쓸 수 없다. ⇒ 쓰기는 인스턴스 **밖**이어야 하고 읽기는 부팅 **중**
이어야 한다. SSM 은 이미 이 데모의 상태 채널이고(heartbeat·usage·health), 인스턴스 역할에
읽기 권한을 최소로 더하면 된다 — **새 리소스를 만들지 않는다.**

### D2 — 방문자가 고르는 단위는 **화면(묶음)** 이고 도메인이 아니다

`BUNDLES` = {fan → fan, store → ecommerce, console → console}.
`BUNDLE_ADDONS` = {store-fulfillment → wms scm, console-<domain> → <domain>}.

🔴 하드 의존(iam)은 **묶음 표에 안 적는다** — `resolve_deps` 가 얹는다. 적으면 같은 사실이
두 곳에 생기고 `DEPS` 가 바뀌는 날 한쪽만 고쳐진다.
🔴 콘솔의 업무 도메인은 **묶음이 아니라 애드온**이다. 콘솔은 그것들 없이 뜨고, 안 뜬 도메인은
그 섹션만 «서비스 시작 필요» 가 된다. 소프트 의존을 묶음에 접으면 「콘솔 하나 켜기」가 전
스택을 끌어와 **선택의 존재 이유를 없앤다.**
🔴 이 표는 `projects.sh`(부팅 셸)와 `handler.py`(Lambda) **두 곳**에 있다 — 다른 런타임이라
피할 수 없다. 갈라지는 것은 피할 수 있고, 가드 (z32)가 두 표를 파싱해 대조한다.

### D3 — 폴백은 `demo-core` 다. **`full` 이 아니다**

파라미터가 없거나 못 읽을 때 무엇으로 뜰 것인가는 결정이다.

🔴 `full` 로 폴백하면 방문자가 «팬만» 을 골랐는데 파라미터 읽기가 한 번 실패한 것만으로
**96 컨테이너가 뜬다** — 비용·웜업 모두 의도와 정반대다. 그리고 더 나쁘게, **폴백이 옛
동작이면 「선택이 저장되지 않는다」는 결함이 영영 안 보인다.**
⇒ 안전한 쪽은 **작은 쪽**이다. `demo-core` 는 이미 이 저장소가 «핵심 경로» 로 정의해 둔
집합이고 `full` 보다 작다. 🔴 폴백이 도는 것을 **말한다**(stderr).

### D4 — 동시 요청은 **합집합**으로, 종료는 **잠금**으로

시작 요청 = 원소 추가(단조). 두 요청이 겹쳐 한쪽이 덮여도 **다시 쓰면** 집합은 둘 다 갖는다
(G-Set). ⇒ 쓴 뒤 다시 읽어 확인하고, 없으면 재시도한다. 🔵 락보다 약하지만 **락이 죽었을 때
데모가 영영 안 켜지는 실패 모드가 없다.**

🔴 **종료는 이 성질이 없다** — 원소 제거는 단조가 아니다. 그래서 종료만 잠금을 쓴다.
🔴 그 잠금도 상호배제를 **보장하지 못한다**(SSM 에 CAS 가 없다). 창을 좁힐 뿐이고, 그 사실이
코드 주석에 적혀 있다. **만료를 반드시 둔다** — 만료 없는 잠금은 Lambda 가 한 번 죽는 순간
데모를 영구히 잠그고, 그 상태의 사용자 표면은 «버튼이 아무 일도 안 함» 이라 진단이 오래 걸린다.

### D5 — «EC2 running» 과 «이 기능 준비됨» 은 **다른 값**이다

`/bundles` 가 묶음마다 7단계를 돌려준다:
`waiting` · `requested` · `booting` · `ready` · `partial` · `stopping` · `unknown`.

🔴 한 값으로 쓰면 방문자가 running 을 보고 링크를 눌러 404 를 만나고 **«고장» 으로 읽는다.**
🔴 `ready` 는 **iam 을 포함한** 필수 도메인이 전부 up 일 때만이다. 빼면 «로그인이 안 되는데
준비 완료» 를 표시하게 된다 — 이 저장소가 반복해서 당한 실패 모드다(MONO-358).
🔴 헬스가 `stale` 이면 **어떤 도메인 상태도 안 믿고** `unknown` 이다(MONO-551 결함 B).

### D6 — 「전체 시작」은 기본 행동에서 **빠지되 남는다**

`<details>` 안으로 넣는다. 지우지 않는 이유: 그 동작은 여전히 유효하다(면접 콜드스타트 전에
미리 다 올려 두는 용도). 요구가 구별한 것이 «기본 행동에서 제외» 이지 «제거» 가 아니다.

### D7 — 이미지·제목·둘러보기는 **절대 기동을 겸하지 않는다**

카드 안에 서로 다른 두 컨트롤이 있고, 그 분리가 **마크업의 모양으로 강제된다**:
`<a data-surface …>` (정적 Vercel 주소) vs `<button data-bundle-start>` (묶음 기동).
🔴 한 요소가 둘을 겸하면 «둘러보러 눌렀는데 EC2 가 켜졌다» 가 되고, 그것은 **요금이 걸린
부작용**이다.

### D8 — 공개 둘러보기는 heartbeat 를 보내지 않는다

heartbeat 를 보내는 것은 **론처 페이지**와 **로그인한 세션**뿐이다. 세 앱의
`POST /api/demo/heartbeat` 는 세션이 없으면 204 no-op 이다.
🔵 역방향도 필요하다: 로그인해서 실시간 기능을 쓰는 동안에는 **론처 탭을 닫았다는 이유만으로
종료되면 안 된다** — 그래서 앱 쪽 heartbeat 가 존재한다.

## 발견한 기존 결함 — 반복 `/start` 가 최대 가동 시간을 리셋했다

`handler.py start()` 가 상태와 무관하게 `_put(STARTED_PARAM, _now())` 를 했다. 그래서 `/start` 를
주기적으로 부르면 `run_sec = now - started` 가 영원히 작게 유지되어 **`max-runtime 180m` 가드가
한 번도 물지 못했다.**

🔴🔴 그 파일의 헤더가 이 시나리오를 **이미 문장으로 적어 두고 있었다**(*"/start 를 반복
호출하면 둘 다 계속 리셋되어 24/7 가동이 가능하다"*) — 그리고 그 이유로 **월 예산 가드를 새로
만들었다.** 즉 이 저장소는 **가드를 하나 더 만들면서 원래 가드는 고치지 않았고**, 새 가드가
지출을 막아 주는 바람에 피해가 눈에 안 띄었다. 최대 가동 시간 축은 그동안 죽어 있었다.

수정: `started` 는 `stopped → start` **전이에서만** 찍는다. `beat` 는 계속 갱신한다(두 값의
의미가 다르다 — beat = «누가 쓰고 있다», started = «이 세션이 언제 시작됐다». 후자를 연장하는
것은 세션 연장이 아니라 **기록을 지우는 것**이다).

## Consequences

- **AMI 재굽기가 필요하다.** `demo-boot.sh` · `demo-selection.sh` · `demo-stack.service` 는
  AMI 에 구워지고 `terraform apply` 로는 도달하지 않는다(`infra/demo/aws/README.md` 의 도달
  경로 표). 🔴 **머지만으로는 런타임에 반영되지 않는다.**
- 부팅 시간이 선택에 따라 달라진다. 「약 10분」은 `full` 의 실측이고, 묶음 하나의 값은
  **아직 안 쟀다** — 그래서 론처에 숫자를 안 적었다.
- `/domain/*` 는 그대로 남는다(고급 영역). 두 축이 공존하는 이유는 **다른 것을 재기** 때문이다:
  도메인 = 구현 단위(running 전제), 묶음 = 제품 단위(stopped 에서도 선택 가능).
