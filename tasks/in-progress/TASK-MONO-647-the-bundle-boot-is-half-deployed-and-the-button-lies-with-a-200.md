# Goal

`2026-09-08` 에 `terraform apply` 로 묶음 라우트 3개(`GET /bundles` · `POST /bundle/start`
· `POST /bundle/stop`)가 배포됐다. **제어 API 쪽은 완성됐다.** 그런데 그 요청을 실제로
수행하는 쪽 — EC2 인스턴스 — 은 **그 개념을 모른다.**

결과: 방문자가 「팬 플랫폼 · 실시간 기능 시작」을 누르면

1. 람다가 선택 `["fan"]` 을 SSM 에 저장하고 인스턴스를 켠다 — **200 을 낸다**
2. 인스턴스는 `demo-boot.sh full` 을 돌린다 — **SSM 선택을 읽는 코드가 없다**
3. **8도메인 전체가 뜬다.** 팬만 골랐는데 예산은 전체 스택만큼 나간다

🔴 **에러가 아니라 «다른 동작» 이다.** 로그에도 안 보이고, 화면은 정상으로 보인다.
핸들러가 다른 원인(라우트 순서)으로 정확히 이 실패를 경고해 뒀는데, 실제로는 **AMI 세대차**
로 같은 자리에 도착했다.

🔴 어제까지는 안전했다 — 라우트가 없어서 버튼이 **잠겨 있었다.** apply 가 그 잠금을 풀었고,
그래서 이 결함은 **오늘 생겼다.**

# 🔴🔴 재굽기 순서 — **2026-09-08 정정 #2. 앞 판이 틀렸다**

이 절의 첫 판은 *"재굽기가 볼륨을 파괴하니 **재굽기 전에** `TASK-MONO-645` 를 수확하라"* 였다.
**틀렸다.** 볼륨이 파괴된다는 사실은 참인데, **켜서 잴 것이 있는지를 안 봤다.**

구워진 AMI(`RepoCommit = 3bc182ecd`)를 열어서 쟀다:

| 축 | 구워진 것 | 지금 `main` |
|---|---|---|
| `V19__seed_more_sample_data.sql` | 🔴 **없음** | 있음 |
| `seed-fan.sh` 의 아티스트 | `a001 a002 a003` | `a001`–`a006` |

⇒ 재굽기 전에 켜면 **645 ②③ 은 잴 대상이 그 인스턴스에 없다.** 그리고 ③ 자체가

새 마이그레이션이 도착하는 유일한 경로가 인스턴스 교체이고, 그것이 볼륨을 새로 만든다.

## 그래서 순서는 이렇다

1. **AMI 재굽기** → `ami_id` 갱신 → `apply` (~55분 · 과금 · 인스턴스 교체)
2. **그 뒤 한 번의 기동 창**에서 전부 수확:
   이 티켓의 검증(묶음 기동이 실제로 되나) · **기동 시간 측정**(아직 한 번도 안 쟀다) ·
   `TASK-MONO-645` ①② · `TASK-MONO-633` · `TASK-MONO-648`(포트폴리오 촬영)
3. 🔵 **창을 두 번 열 이유가 없다.**

## 🔵 그래도 이 티켓의 가드는 여전히 필요하다

재굽기는 **지금의 거짓말**을 없앨 뿐이다. 세 배포 경로 — Vercel 머지 · `terraform apply` ·
AMI 재굽기 — 가 **서로 다른 속도로 나가는 구조**는 그대로다. 다음에 `demo-up.sh` 가 바뀌는
날 똑같이 재발하고, 그때도 버튼은 200 을 내며 다른 일을 한다(§ Failure Scenarios 5).

## AC-1 — 세대가 어긋나면 묶음 기동을 거절한다

- [ ] 🔴 **판단은 «AMI 의 `RepoCommit` 이 묶음 기동을 아는가» 로 한다.** 하드코딩 스위치로
      끄지 마라 — 그러면 재굽기 뒤에 **이 코드를 또 고쳐야 하고**, 그 티켓이 안 만들어지면
      기능이 영원히 꺼진 채로 남는다. 세대를 읽으면 재굽기 순간 **저절로 풀린다.**
- [ ] 🔴 «안다» 의 판정을 **무엇으로 할지 정하고 근거를 적어라.** 후보: ① AMI 태그
      `RepoCommit` 이 `9f0fcd2d6` 의 자손인가 ② 인스턴스에서 파일을 직접 grep. ①은 인스턴스가
      꺼져 있어도 되지만 조상 판정이 필요하고, ②는 정확하지만 **running 이어야** 한다 —
      즉 «켜기 전에 막는다» 는 목적에 ②는 못 쓴다. 이 제약을 적고 고르라.
- [ ] 거절은 **`bundle_start` 에서** 한다 — 행위가 일어나는 자리다. `/bundles` 에서만
      막으면 API 를 직접 부르는 경로가 남는다.

# Failure Scenarios

1. **하드코딩으로 묶음 기동을 꺼 둔다** → 재굽기 뒤에도 꺼진 채로 남고, 그걸 켜는 티켓이
   안 만들어지면 `ADR-MONO-071` 이 영원히 죽는다.
2. **`/start` 까지 같이 막는다** → 지금 되는 유일한 기동 경로를 없앤다.
3. **`/bundles` 에서만 막는다** → API 를 직접 부르는 경로가 남는다. 가드는 **행위가
   일어나는 자리**에 있어야 한다.
4. **644 와 합친다** → 원인이 다르고 처방이 다르다. 하나를 고쳐도 다른 하나가 남는다.
5. **재굽기를 해서 증상만 지우고 닫는다** → 세 배포 경로는 계속 다른 속도로 나간다.
   다음에 `demo-up.sh` 가 바뀌는 날 똑같이 재발한다.
6. **가드가 AWS 를 부른다** → CI 에 자격증명이 없어 영구 빨강이거나 영구 skip 이 된다.

## 🔴 이 티켓은 닫히지 않는다

AC-0 이 이 상황을 예고해 뒀다: *"그 사이 소유자가 재굽기를 했다면 재현 조건이 사라진다 —
**그때도 티켓을 닫지 마라.** 판정은 «지금 세대가 맞나» 가 아니라 **«어긋났을 때
거절하는가»** 다."*

재굽기는 **오늘의 거짓말을 없앤다.** 이 티켓이 막으려는 것은 **다음번**이다 —
세 배포 경로(Vercel 머지 · terraform apply · AMI 재굽기)가 서로 다른 속도로 나가는
구조는 그대로이고, 다음에 인스턴스 실행 파일이 바뀌는 날 똑같이 재발한다.
⇒ AC-1(세대를 읽고 거절) · AC-2(화면이 말한다) · AC-3(가드)은 **그대로 남는다.**

🔴 AC-0 의 지시대로, 세대가 맞는 지금은 **인위적으로 어긋난 값을 넣어서** 거절을 재야 한다.
