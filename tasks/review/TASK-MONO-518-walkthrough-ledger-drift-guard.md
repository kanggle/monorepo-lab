# Goal

티켓이 `done/` 으로 넘어갔는데 워크스루 행이 그것을 반영하지 않으면 **CI 가 빨개진다.**

# Scope

## In Scope

- `scripts/check-walkthrough-ledger-drift.sh` 신설 + `.github/workflows/ci.yml` 등록
- 술어: § 6 표의 각 행에서 인용 티켓 ID 를 뽑고 → 그 티켓의 현재 큐를 조회 →
  **`done/` 인데 행이 해소 표시(`✅` / `~~취소선~~` / `🔵`)를 안 달았으면 FAIL**
- 반대 방향: 표에 없는 열린 데모 티켓 검출은 **이번 범위 밖**(§ Out of Scope 사유 참조)

## Out of Scope

  `demo` 태그 규약을 먼저 세우는 별건
- 워크스루의 다른 표(§0 계정 · §1 URL · §2~4 화면 · §7 트러블슈팅) — 티켓을 인용하지 않는다

## AC-1 — 🔴 술어를 **두 번** 고쳤다. 둘 다 실측이 잡았다

**① 행 전체 → tracking 열.** 첫 판은 행 어디서든 `TASK-` 를 뽑았고, 즉시 **오탐**을 냈다:
`/erp/delegation` 행은 `TASK-ERP-BE-043`(**ready**)를 tracking 하면서 본문에서
*"`TASK-ERP-BE-041` 이 닫히자 예측이 실측으로 확인됐다"* 라고 **서술**한다. 그 문장은 행이
옳다는 증거인데 가드가 그것을 물었다 — 그런 가드는 **이력을 적지 말라고 가르친다.**
⇒ tracking 열이 "이 행이 무엇에 관한 것인가" 이고, 본문 인용은 맥락이다.

**② "어디든 ✅" → 선두 상태 이모지.** 이게 더 나쁜 쪽이었다. `/ledger` 행은 상태가 🟡 인데
본문 측정 목록에 *"시산표 **3원소** ✅"* 라고 **체크표시로** ✅ 를 쓴다. 그 장식 하나가 행을
"해소됨" 으로 읽히게 했고, 그래서 **AC-3 ② 네거티브가 안 물었다** — 예외를 지워도 아무 일이
없었다.

🔴 **그 두 사실은 한 결함의 양면이다**: *잘못된 이유로 통과하는 가드* 와 *한 번도 행사되지
않는 예외*. 예외가 안 물어서 술어가 틀렸음을 알았다 — **네거티브 테스트가 없었으면 이 가드는
초록인 채로 3행을 영영 못 봤다.**

## AC-2 — 오탐 방지

`done ⇔ ✅` 단순 대응을 쓰지 않았다. 예외 목록 + **사유 필수**(사유 없으면 FAIL)로 했고,
파일 헤더에 *"행이 그냥 낡았으면 여기 넣지 말고 행을 고쳐라"* 와 이번 회차의 비율(고친 4 :
예외 4)을 적어 다음 사람이 예외를 기본값으로 읽지 않게 했다.

## AC-3 — 네거티브 **3종** (티켓은 2종을 요구)

```
① 해소 표시 제거 (SCM-BE-059 행의 ✅/취소선)
     exit=1 · findings=1 · 그 행만 지목                         ✅
② 예외 제거 (PC-FE-273)
     1차: exit=0 — 안 물었다 🔴  ⇒ 술어 결함 발견(위 AC-1 ②)
     술어 수정 후: exit=1 · findings=1 · 그 행만 지목            ✅
③ 사유 없는 예외 한 줄 추가 (`TASK-BE-999`)
     exit=1 · "carries no reason"                              ✅
```

🔵 ③ 은 티켓이 요구하지 않았지만 넣었다 — 사유 필수가 **강제되는지**를 재는 유일한 술어다.

## AC-4 — 러너

`ci.yml` 에 `walkthrough-ledger-drift` 잡 신설. `paths-filter` 는 **순수 positive**
(부정 패턴 0 — `MONO-074/075` quirk):

```
docs/guides/interview-demo-walkthrough.md
scripts/check-walkthrough-ledger-drift.sh
scripts/walkthrough-ledger-exceptions.txt
tasks/**
projects/*/tasks/**
```

🔴 **큐 경로가 load-bearing 이다** — 이 드리프트의 가장 흔한 도착 경로는 **워크스루를 한 줄도
안 건드리는 close chore** 다. 문서 경로만 걸면 가드가 정확히 그 경우에 안 돈다.
`code-changed` 와 AND 하지 않는다(도착 경로가 전부 비-코드다).

## AC-5 — `set -euo pipefail` 자체 복제 ✅

🔵 그리고 실측 하나: 네거티브 ① 을 `| sed` 로 파이프해서 봤더니 **`rc=0`** 이 찍혔다 —
`tail`/`sed` 의 종료코드다. 파이프 없이 다시 재서 `exit=1` 을 확인했다. 가드의 종료코드를
파이프 너머로 읽으면 CI 가 빨개질 것을 초록으로 읽는다.

## 🔵 성능 — 이것도 술어의 일부였다

첫 판은 티켓 인덱싱을 `basename`/`dirname`/`grep -oE` 로 파일마다 돌렸다. 이 저장소의 task
파일은 **2238개** = 약 9000회 프로세스 spawn 이고, Windows/msys 에서 **5분 타임아웃을 넘겨
행(hang)처럼 보였다**. 파라미터 확장 + `[[ =~ ]]` 로 바꿔 in-process 로 만들었다 — 러너에서
도는 가드가 로컬에서 못 돌면 아무도 안 고친다.

# Edge Cases

- **티켓이 `backlog/`·`archive/` 로 간 경우** — done 이 아니므로 FAIL 대상 아님. 다만 행이
  가리키는 티켓이 **어디에도 없으면**(오타/삭제) 그것도 드리프트 ⇒ FAIL
- **한 행이 티켓 2개를 인용** — 하나라도 done 이면 해소 표시를 요구할지, 전부 done 일 때만
  요구할지 정해야 한다(현재 표에 `TASK-SCM-BE-060 ④` 같은 형태가 있다)
- **가드가 `git ls-files` 기반이면** 스테이징 전 로컬 실행이 가짜 드리프트를 낸다 —
  헤더에 적을 것(`check-index-queue-drift.sh` 가 같은 성질)

# Failure Scenarios

- 🔴 **술어를 "🔴 행만 검사" 로 좁힌다** → MONO-517 이 놓칠 뻔한 stale 5건과 **정확히 같은
  집합**을 못 본다. 검사 대상은 **티켓을 인용하는 모든 행**이다
- 🔴 **예외 목록에 사유를 안 적는다** → 다음 사람이 예외를 "그냥 통과시키는 목록" 으로 읽고
  진짜 stale 을 거기 넣는다
- 🔴 **가드를 만들고 표를 안 고친 채 머지** → CI 가 즉시 RED. AC-0 이 그 순서를 강제한다
