# Goal

`demo-up.sh erp` 를 띄우면 콘솔 `/erp/delegation` 의 read-model 위임 뷰가 **찬다.**
워크스루 §6 은 그것을 `✅ 해소 (2026-08-12)` 로 기록했다.

**그런데 그 뷰를 채우고 있는 행은 데모 시드가 만든 위임이 아니라, 그 해소를 검증하던
세션이 자기 확인용으로 만든 프로브 행이다.** 시드가 만든 위임은 read-model 에 **없다.**

실측 (2026-08-16, erp 8/8 healthy · 기존 볼륨):

| grantId | reason | 생성(UTC) | `approval` | `read-model` |
|---|---|---|---|---|
| `dgr-019ff4f6-0a61-76db-a9cc-9c1cf4f68602` | **데모 시드 — 부재 시 전결** | 08-12 07:53 | ✅ | ❌ **없다** |
| `dgr-019ff68b-1ed3-73ee-935b-b2530275f40a` | BE-043 라이브 프로브 | 08-12 15:15 | ✅ | ✅ |

⇒ `/api/erp/approval/delegations` = **2** · `/api/erp/read-model/delegations` = **1**.

**프로브 행을 지우면 이 볼륨에서 그 화면은 빈다.** 계측기가 대조군을 오염시킨 형태다 —
`✅ 해소` 판정이 **자기가 만든 데이터로 자기를 판정**했다.

# 🔴 정상 설명 두 가지를 먼저 배제했다 (결함이라고 부르기 전에)

발굴 중 실제로 수행한 반증이다. 착수자는 **다시 하지 말고 이어서 하라**.

| 가설 | 왜 그럴듯했나 | 반증 |
|---|---|---|
| ① 투영이 `(delegatorId, scope)` 로 키를 잡아 **최신 하나만** 남긴다 | 두 위임은 `delegatorId` 가 같고 둘 다 `scope=GLOBAL` 이다 — 그렇다면 1행이 **정상**이다 | `DelegationFactProjJpaEntity` 의 `@Id` 는 **`grantId`** 이고 클래스 주석도 *"One row per grantId (= aggregateId)"* ⇒ 두 grant 는 두 행이어야 한다 |
| ② 투영이 **사원 투영에 없는 피위임자**를 거른다 | 조인 기반 필터라면 자연스러운 동작 | 두 피위임자 **둘 다** `/api/erp/read-model/employees` 에 있다(각각 1건 매치). 날짜 필터도 아니다 — 둘 다 현재 유효 구간이고 `status=ACTIVE` |

⇒ 남는 설명은 **봉투 결함 시절 발행된 이벤트가 버려졌고 아무도 재생하지 않았다**는 것이다.
`TASK-ERP-BE-043`(봉투의 `aggregateId`/`tenantId` 부재) 수정은 `396fc982c` **2026-08-13
01:54Z** 로 두 행보다 나중이고, 08-12 15:15 의 프로브는 그 **개발 중 로컬 수정 바이너리**로
만들어졌다. 즉 *"수정 이후에 만든 것은 투영되고, 이전 것은 영영 안 된다."*

🔴 **이 인과는 아직 가설이다** — AC-0 이 그것을 재는 일이다. 재생 여부를 결정하기 전에
**이벤트 평면에서 실제로 무엇이 있었는지**(토픽에 남은 원본 봉투 / DLT / 컨슈머 오프셋)를
확인하라. 확인 불가면 **확인 불가로 적는다** — 세 번째 추측을 심지 않는다.

# 🔴 왜 아무도 못 잡았나 — 시드에 **볼 술어가 없다**

`seed-erp.sh` 는 프로젝션을 **한 축만** 확인한다:

```
[seed:erp] 프로젝션 사원 4/4 반영 확인 (read-model)     ← employees 는 센다
                                                        ← delegations 는 한 번도 안 센다
```

그리고 위임 생성은 멱등이라(`존재  위임 이운영에게 전결`) **재실행해도 이벤트를 다시 쏘지
않는다** ⇒ 자력 복구 경로가 없다.

🔵 **신선 볼륨에서는 초록이다**(수정된 바이너리가 봉투를 제대로 실어 보낸다). 그래서 CI 도,
새로 볼륨을 만든 사람도 이것을 영원히 못 본다 — `TASK-MONO-535` 와 **정확히 같은 클래스**:
결함은 파일이 아니라 **이 볼륨의 데이터 이력**에 있다.

# Edge Cases

- 위임이 **양쪽 다 0** 인 경우(첫 기동, 아직 시드 전) — 불일치가 아니므로 경고하지 않는다.
  🔴 그런데 `0 == 0` 은 *"둘 다 못 물어봤다"* 로도 성립한다. 비-2xx 는 **0 이 아니라 실패**로
  가른다(이 저장소가 반복해서 틀린 자리).
- `read-model` 이 **더 많은** 경우(투영에만 있는 유령 행) — 방향이 반대지만 역시 불일치다.
  경고 문구가 방향을 말해야 한다.
- 볼륨이 초기화되면 이 결함은 사라진다 ⇒ AC-0 을 건너뛰고 착수하면 **없는 결함을 고친다.**

# Failure Scenarios

- 술어를 `dbquery` 로 짜면 도커 컨트롤 플레인 포화 때 **빈 문자열**이 되어 오탐이 난다
  (`dbquery` 는 `2>/dev/null` 이라 데몬 오류와 쿼리 오류가 구분되지 않는다 — 이번 발굴에서
  `seed-fan.sh` 가 실제로 그 이유로 2건 실패했다).
- 경고를 "늘 켜 두는" 형태로 만들면 다음 사람이 그것을 배경 소음으로 읽는다 ⇒ AC-1 이
  *"정상일 때 안 붙는다"* 를 요구하는 이유다.
- 프로브 행을 "정리" 한답시고 지우면, 그 순간 화면이 비면서 **이 티켓이 서술한 상태가
  더 나빠진다.** 지우지 말고 **시드 행이 왜 없는지**를 해결하라.
