## 🔴 술어가 자기 스크립트의 다음 단계에 의해 무효가 된다

`infra/demo/seed/seed-finance.sh` 의 `topup()` 은 **의도적으로** 응답 코드를 안 믿는다.
그 판단 자체는 옳고, 주석에 이유가 적혀 있다:

> *"고정 `Idempotency-Key` 를 쓰므로 2회차는 서버가 저장된 2xx 를 **재생**한다. 즉 '이번
> 실행이 돈을 넣었나' 는 200 으로 판별 불가능하다. 여기서는 **잔액 자체**가 술어다:
> 목표 이상이면 도달, 미만이면 실패 — **재생이든 최초든 결론이 같다**."*

마지막 문장이 **참이 아니다.** 결론이 같으려면 *"잔액은 입금 말고는 안 변한다"* 가 성립해야
하는데, **바로 다음 단계가 그 잔액을 쓴다**:

```
TOPUP_MINOR=500000
topup "계좌 A 입금" ...   →  A = 500,000
topup "계좌 B 입금" ...   →  B = 500,000
이체 A→B 100,000         →  A = 400,000 · B = 600,000     ← 여기서 술어의 전제가 깨진다
```

2회차에는 입금이 재생(=돈 안 들어옴)되고 A 는 여전히 400,000 이므로
`after(400000) >= want(500000)` 이 거짓 → `seed_fail`.

🔵 **A 만 실패하고 B 는 통과하는 비대칭이 지문이다.** B 는 이체를 *받아서* 600,000 ≥
500,000 이라 통과한다. 실패 방향이 정확히 이체 방향과 일치한다 — 우연이 아니다.

⇒ **1회차 성공은 "고쳐져 있다"의 증거가 아니었다.** 이 시드는 **한 번도 재실행된 적이 없는
계좌**에서만 통과한다.

## 왜 지금까지 안 보였는가 (그리고 왜 지금 보이는가)

그래서 `demo-stack.service` 는 **초록**이었고, 로그를 펼쳐 읽지 않는 한 아무도 몰랐다.

# Goal

시드가 **재실행에도 정직하게 통과**한다. 그리고 그 통과가 *"입금이 성립해 있다"* 를 뜻한다 —
*"지금 잔액이 우연히 목표 이상이다"* 가 아니라.

# Scope

## In Scope

- `seed-finance.sh` 의 `topup()` 술어를 **입금 사실**에 대한 것으로 바꾼다.
  구현자가 AC-0 에서 확인 후 택일하고 **근거를 적을 것**:
  - (a) **목표를 실제 기대값으로 낮춘다** — 이체 후 A 의 정상 잔액은 400,000 이므로
    계좌별 기대치를 따로 준다. 🔴 가장 작은 변경이지만 **가장 약하다**: 상수 두 개가
    이체 금액과 **말없이 결합**되고, 이체 금액이 바뀌면 다시 깨진다.
  - (b) **입금 거래의 존재로 판정한다** — 거래내역에서 시드 입금(reason/idempotency key)을
    찾는다. 술어가 *"입금이 성립했나"* 와 정확히 일치한다.
  - (c) **하한을 이체를 반영해 계산한다** — `want = TOPUP_MINOR - (이 시드가 옮긴 금액)`.
    (a)보다 낫지만 여전히 시드 내부 순서에 의존한다.
- 🔴 **어느 쪽이든 "재생이든 최초든 결론이 같다" 는 주석을 고칠 것.** 그 문장이 틀렸다는
  것이 이 티켓이고, 고친 코드 옆에 틀린 이유가 남아 있으면 다음 사람이 같은 추론을 한다.

## Out of Scope

- **시드 전체를 멱등으로 재설계**하는 것. 다른 도메인 시드(wms·scm·erp·ecommerce·fan)는
  같은 왕복에서 `실패 0` 이었다 — 🔵 다만 **그것이 "그들은 안전하다"는 뜻은 아니다**
  (AC-2 참조).
- `demo-up.sh` 의 종료코드 정책 → `TASK-MONO-553` 에서 이미 결정됐다. **되돌리지 말 것.**
  유닛이 red 인 것은 정확한 보고이고, 고칠 것은 **red 의 원인**이다.
- finance 백엔드의 입금/이체 로직. 서버는 시킨 대로 했다 — 결함은 **시드의 술어**다.

# Acceptance Criteria

**AC-0 — 재확인 (verify-then-act).** ✅ **완료 (2026-08-18, origin/main @ `9f815273e`)**
`seed-finance.sh` 의 `topup()` · 이체 블록 · 상수를 다시 읽고 **A 의 이체 후 기대 잔액을
산술로 확인**했다 — 위 400,000 은 로그 관측값이었으므로 코드에서 다시 유도했다:

```
TOPUP_MINOR    = 500000        (L158)
TRANSFER_MINOR = 100000        (L200)
⇒ A = 500,000 - 100,000 = 400,000     ← 관측 400000 과 일치
⇒ B = 500,000 + 100,000 = 600,000     ← 관측 600000 과 일치
```

🔴🔴 **그리고 답은 상수 옆 주석에 이미 적혀 있었다:**

```
TOPUP_MINOR=500000   # ₩5,000.00 — 이체 100,000 + 홀드 여유
```

작성자는 **이체가 잔액을 깎는다는 것을 알고** 입금액을 그만큼 크게 잡았다. 그런데
**같은 함수의 술어는 그 사실을 반영하지 않는다**(`after >= 500000`). 상수는 이체를
계산에 넣었고 술어는 안 넣었다 — 한 파일 안에서 두 곳이 어긋나 있었고, 어긋난 쪽이
술어다.

**AC-1 — 재실행이 통과한다. 🔴 대조군 필수.** ✅ **완료 (2026-08-18 UTC)**

채택한 안은 **(b) 입금 거래의 존재로 판정**이다. `GET /{id}/transactions?type=TOPUP` 이
계약에 실재한다(`account-api.md:213` · `TransactionType.TOPUP`). (a)/(c)를 버린 이유는
이 티켓이 적어 둔 그대로다 — 둘 다 **이체 금액과 말없이 결합**되어 다음 변경에서 재발한다.
(b)는 잔액이 나중에 어떻게 쓰이든 무관하고 시드 내부 순서에도 결합하지 않는다.

잔액은 계속 읽지만 **판정이 아니라 *생성/재생* 을 가르는 보고용**으로만 쓴다.
🔵 그 두 역할을 한 값에 겹쳐 쓴 것이 이 결함의 형태였다.

가드 **(z8)** 을 `verify-demo-wrapper.sh` **정적** 구간에 신설했다. 네 칸 전부 실측:

| 칸 | 내용 | 결과 |
|---|---|---|
| (1) | 1회차 (대조군) | `실패 0` |
| (2) | **이체 A→B 후 2회차** (bite) | `실패 0` |
| (3) | 입금이 성립하지 않음 (음성 대조군) | **실패** ✓ |
| (4) | 거래내역 조회 5xx | **실패** ✓ + 사유가 *"판정 불가"* 로 구분됨 |

🔴 **고침 전 코드에 물린다 — 단독과 wrapper 안에서 두 번 확인했다.** 그리고 해네스가 낸
실패 두 줄이 라이브 호스트 관측 로그와 **바이트 단위로 같다**:

```
✗ 계좌 A 입금 — 입금 후 ledger=400000 로 목표 500000 미만이다
기존  계좌 B 입금 — ledger 600000 (재생, 이중 입금 없음)
```

닮은 실패가 아니라 **그 실패**를 재현했다. (1)은 고침 전에도 통과하므로 무는 자리는 정확히
(2)다 — **한 번만 돌리는 가드였다면 아무것도 안 지켰다.**

🔴🔴 **가드를 한 번 잘못 만들었고 고쳤다 — 기록해 둔다.** 처음엔 `topup_txns()` 를 추출
앵커 목록에 넣었는데, 그러면 고침 전 코드가 **행위 셀 (2)가 아니라 앵커 자기점검에서** 죽고
실패가 *"앵커가 갈라졌다"* 로 보고된다. 무는 것은 맞지만 **엉뚱한 이름에 귀속된 실패**라,
다음 사람은 술어 결함이 아니라 리팩터링 사고를 찾으러 간다. 앵커에는 **추출 기계장치**만
남기고 구현의 유무는 행위가 판정하게 했다.

🔵 가드는 코드를 **복사하지 않고 원본에서 추출**한다 — 복사본을 검사하는 가드는 원본이
갈라져도 초록이다. 추출이 빗나가면 조용히 통과하지 않고 그 자리에서 죽는다.

**AC-2 — 형제를 세라.** ✅ **완료 (2026-08-18 UTC) — 같은 결함 0건. 어떻게 셌는지 적는다.**

*"이번 왕복에서 실패 0"* 은 근거로 쓰지 않았다(finance 도 1회차엔 실패 0 이었다). 대신 **두

② 걸린 것마다 *"그 시드가 자기가 만든 그 값을 나중에 소비하는가"* 를 코드로 확인.

| 시드 | 수치 임계 술어 | 판정 |
|---|---|---|
| **finance** | `after -ge want` (L174) | 🔴 **결함** — 같은 시드의 이체가 그 잔액을 쓴다 |
| erp | `got -ge want` (L434·437) | 🟢 안전 — 프로젝션 지연 대기다. `want` = 이 시드가 만든 사원 수이고 **이 시드는 사원을 줄이지 않는다**(단조). 🔵 게다가 같은 파일 L457-459 가 결재함에 대해 *"≥1 로 재지 않는다 — 승인하면 정상적으로 줄어든다"* 며 **이미 이 교훈을 적용해 두었다** |
| scm | `after -gt before`(L213) · `hist_after -gt hist_before`(L287) | 🟢 안전 — **델타형**(*"늘었는가"*)이라 이 결함 형태가 성립하지 않는다 |
