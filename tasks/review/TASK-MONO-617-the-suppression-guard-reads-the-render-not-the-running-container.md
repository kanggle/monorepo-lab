# 🔵 이 저장소에 **같은 모양의 선례가 이미 있다**

`check-label-drift.sh`(`TASK-MONO-553`)가 구조적으로 동일한 문제를 푼다 — *"초록인데 실제로는

```
· docker ps        → 초록이다. 옛 컨테이너도 running + healthy 다.
· demo-status.sh   → 컨테이너를 셀 뿐 «어느 주소로 열리는지» 모른다.
· compose 종료코드 → 0 일 수 있다.
· HTTP 200         → 옛 호스트명으로 물으면 열린다.
⇒ 어긋난 것은 오직 라벨 안의 호스트명이었다. 그러니 라벨을 직접 읽는다.
```

배선도 같이 있다: `demo-up.sh:410` 이 부팅마다 `post_up_call` 로 돌리고,
`verify-demo-wrapper.sh` **(z5)** 가 *"그 스크립트가 존재하는가"* 를 정적으로 지킨다.
⇒ **런타임 관측자 + 그 관측자의 존재를 지키는 정적 가드**라는 쌍이 이 저장소의 기존 형태다.

| `docker` 명령 없음 / 데몬 불가 | `rc=2` 판정 불가 (🔴 «억제됨»으로 읽지 말라고 메시지에 명시) |
| 렌더가 0행 | `rc=2` — «억제됨»이 아니라 «`config` 실패» |
| **그 프로젝트의 컨테이너가 0개** | `rc=2` — 🔵 **양성 대조군을 판정 안에 넣었다.** 0건이 «정말 없다»와 «docker 가 이 프로젝트를 못 본다»를 구별하지 못하기 때문 |
| 위반 발견 | `rc=1` + 컨테이너 이름·상태·생성시각 |

## AC-3 — 🔴🔴 bite. **실컨테이너 4칸**, 그리고 **bite 가 내 결함을 잡았다**

로컬 docker 데몬을 띄워 라벨을 단 실컨테이너로 돌렸다. 주입은 매번 **먼저 단언**했다.

|---|---|---|---|
| ① 대조군 | `project=ecommerce, service=ecommerce-gateway` 1개 · web-store 라벨 **0개** | rc=0 | ✅ **rc=0** |
| ② 주입 | web-store 라벨 컨테이너 **1개** 추가 | rc=1 | ✅ **rc=1** — `bite617-inj state=running` 을 이름으로 댔다 |

「위반을 봤기 때문」인지 구별되지 않는다. 실제로 대조군 없이 돌린 첫 실행이 **rc=2** 였고,
그것이 바닥이 살아 있다는 독립 증거이기도 하다.
