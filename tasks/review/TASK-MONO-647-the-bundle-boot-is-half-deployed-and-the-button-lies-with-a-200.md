# 🟢 구현 (2026-09-10 UTC · `in-progress`)

## AC-1 — 판정을 무엇으로 하는가, 그리고 **왜 저장소에서 하는가**

🔴🔴 **티켓이 남긴 두 후보를 실측해서 둘 다 떨어뜨렸다.**

| 후보 | 왜 못 쓰나 (실측) |
|---|---|
| ② 인스턴스에서 파일 직접 grep | **`running` 이어야 한다.** 이 가드의 목적이 「켜기 전에 막는다」이므로 성립하지 않는다. (`deployed-ami.env` 머리말의 실측: stopped 이면 SSM 관리 대상도 아니다) |
| ① Lambda 가 런타임에 AMI 태그 `RepoCommit` 을 읽는다 | **두 겹으로 막힌다.** (a) Lambda IAM 에 **`ec2:DescribeImages` 가 없다** — `main.tf` 의 정책은 `StartInstances`/`StopInstances`/`DescribeInstances` 뿐이고, `DescribeInstances` 는 `ImageId` 는 주지만 **그 이미지의 태그는 안 준다.** (b) 태그를 읽어도 **Lambda 는 git 조상 판정을 못 한다.** |

⇒ 🔴🔴 **이 부류의 사실은 런타임에 존재하지 않는다.** 「`main` 이 앞서 나갔다」의 한쪽 항이
저장소이고, 저장소는 Lambda 안에 없다. 그래서 판정을 **저장소에서 하고 apply 가 값을 실어
나른다** — `infra/demo/aws/ami-bundle-capability.sh` → `data "external"` → Lambda env.

**술어**: 「AMI 의 `RepoCommit` 이 `9f0fcd2d6`(ADR-MONO-070/071 본체)의 **자손인가**」.
그 커밋이 건드린 인스턴스 실행 파일이 정확히 셋이다(실측 `--stat`): `demo-boot.sh`(+49) ·
`demo-stack.service`(+21) · `projects.sh`(+66). 즉 「묶음을 안다」 = 「그 세 파일의 그 판을
갖고 있다」 = 「그 커밋의 자손이다」.

🔵 **하드코딩 스위치가 아니다**(AC-1 이 금지한 것). 값이 `deployed-ami.env` 의 `REPO_COMMIT`
에서 **유도**되고 그 파일은 `bake.sh` 가 기계로 쓴다. 재굽기는 `ami_id` 교체 apply 를
**어차피 필요로 하고**, 그 apply 가 이 값을 다시 계산한다 ⇒ **저절로 풀린다. 고칠 코드가 없다.**

🔴 **거절은 `bundle_start` 안, 그리고 어떤 상태 변경보다 앞이다** — `_add_to_selection` 도,
`ec2.start_instances` 도 하지 않는다. 관측된 결함이 「200 을 내고 8도메인을 띄운다」였고 그
비용이 **전체 스택 분량**이므로, 막을 거면 돈이 나가기 전에 막아야 한다.
🔵 `/start`(전체 스택)는 **안 막는다**(Failure 2). 코드 = **409**: 재시도로 풀리는 성질이
아니므로 5xx(재시도 유도)가 아니라 4xx 다.

## AC-2 — 화면이 무엇이 필요한지 말한다

`/bundles` 응답에 `bundle_boot_supported` + `bundle_boot_blocked`(사유 문구 포함)를 더했고,

방문자에겐 둘 다 「지금은 못 한다」지만 운영자의 처방이 다르다.

그때 `bundle_boot_supported === false` 는 거짓이라 `bundleBlocked = null` 이 된다.
즉 **오늘의 화면은 안 바뀐다.**

# Failure Scenarios

1. **하드코딩으로 묶음 기동을 꺼 둔다** → 재굽기 뒤에도 꺼진 채로 남고, 그걸 켜는 티켓이
   안 만들어지면 `ADR-MONO-071` 이 영원히 죽는다.
2. **`/start` 까지 같이 막는다** → 지금 되는 유일한 기동 경로를 없앤다.
3. **`/bundles` 에서만 막는다** → API 를 직접 부르는 경로가 남는다. 가드는 **행위가
   일어나는 자리**에 있어야 한다.
4. **644 와 합친다** → 원인이 다르고 처방이 다르다. 하나를 고쳐도 다른 하나가 남는다.
5. **재굽기를 해서 증상만 지우고 닫는다** → 세 배포 경로는 계속 다른 속도로 나간다.
   다음에 `demo-up.sh` 가 바뀌는 날 똑같이 재발한다.
6. **가드가 AWS 를 부른다** → CI 에 자격증명이 없어 영구 빨강이거나 영구 skip 이 된다.

**어긋남 1건**이 되고 처방은 *"닫는 행위는 재굽기다(~55분 · 과금)"* 다.

644 가 `index.html` 에서 바꾼 것은 `<script>` 안의 상태기계뿐이고, `demo-up.sh` 가 그
파일에서 **추출하는 것**은 선언 속성뿐이다 — `data-surface`/`data-served`/`data-host`/
`data-demo-probe(-path)`. 즉 *"구운 데모 호스트는 서빙 중인 론처가 약속하는 것을 서빙하지
않습니다"* 는 이 변경에 대해 **참이 아니다.**

🔵 판정자가 파일 내용 전체를 비교하는 것은 설계 선택이다(추출기를 두 벌로 만들면 한쪽만
고쳐진다). 하지만 `index.html` 은 **머지 = 배포**라 이 영역에서 가장 자주 바뀌는 파일이고,
그래서 이 가드는 앞으로도 계속 이렇게 빨개진다. ⇒ **`TASK-MONO-649`** 로 기안했다.
