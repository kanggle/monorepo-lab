# 배경

`.github/workflows/_integration.yml` 은 테스트 리포트를 **`if: failure()`** 로만 올린다.

```yaml
- name: Upload integration test reports on failure
  if: failure()
  uses: actions/upload-artifact@v4
```

⇒ **통과한 통합 잡은 아티팩트를 하나도 남기지 않는다.** 8개 호출자 전부.

## 이미 두 번 값을 치렀다

1. **`TASK-MONO-541`** 이 함정으로 기록한 것 — *"재실행 후 잡이 `success` 인데
   `gh run download` 아티팩트는 여전히 `fail=1`"*. 당시 사유를 *"그 이름의 아티팩트가
   1차 시도분 하나뿐"* 이라고 적었는데, 🔴 **그 사유가 정확하지 않다**: 원인은 `gh` 의
   재시도 동작이 아니라 **업로드 조건**이다 — 성공한 재실행은 **아무것도 올리지 않으므로**
   1차 시도분이 유일하게 남은 것이다. 결과는 같지만 **원인이 다르고**, 틀린 원인은 다음
   사람을 `gh` 쪽으로 보낸다.
2. **`TASK-MONO-542`** 의 AC-2 는 *"그 잡의 아티팩트에서 네 값을 읽어 적는다"* 를
   요구했는데 **초록 회차엔 읽을 아티팩트가 없어 충족 불가**였다. AC-3 bite 회차(실패)의
   아티팩트로 우회했다.

⇒ 이 저장소의 AC 관용구 — *"`tests`/`failures`/`errors`/`skipped` 네 값을 아티팩트에서
읽어라"* — 가 **성공 경로에서 작동하지 않는다.**

## 🔵 인접한 우려는 이미 막혀 있다 (주장이 아니라 확인한 것)

*"Docker 미검출 → `disabledWithoutDocker` 전량 스킵 → `BUILD SUCCESSFUL`"* 은 로컬에서
실제로 일어났지만(`MONO-541`·`542` 양쪽 관측) **CI 에서는 일어날 수 없다** —
`_integration.yml` 에 `docker info` 스텝이 `continue-on-error` 없이 있어서 Docker 가
없으면 잡이 먼저 죽는다. **이 티켓은 그 축이 아니다.**

## 남는 진짜 공백

**발견된 테스트가 0개여도 초록이고, 그 회차엔 셀 수 있는 산출물이 하나도 없다.**
태그 필터 변경 · 모듈 오설정 · 클래스 네이밍 규칙 변경으로 스위트가 조용히 비어도
Gradle `test` 태스크는 성공하고, 나중에 되짚을 기록도 남지 않는다.

🔴 이 저장소가 이미 이름 붙인 실패 모드다 — *"0건 ≠ 없음"*. 여기서는 숫자가 낡는 게
아니라 **애초에 존재하지 않는다.**

# Scope

세 갈래가 있고 **셋 다 할 필요는 없다** — AC-1 이 어느 쪽인지 정한다.

1. **(a) 업로드 조건 완화** — `if: failure()` → `if: '!cancelled()'`. 가장 단순하지만
   8개 잡 × 매 실행마다 저장 비용이 붙는다.
2. **(b) 0-발견을 실패로** — 통합 태스크가 테스트를 하나도 발견하지 못하면 빌드를 깨뜨린다.
   저장 비용 0.
3. **(c) 카운트를 잡 요약에 출력** — `afterSuite` 로 네 값을 `$GITHUB_STEP_SUMMARY` 에.
   저장 비용 0이고 초록 회차에도 숫자가 남는다.

## Out of Scope

- `docker info` 게이트 — 이미 올바르다(§배경).
- 개별 프로젝트의 테스트 내용.
- 유닛 테스트 잡 — **다만 AC-4 가 같은 패턴이 다른 워크플로에도 있는지 센다.**

      `docker info` 스텝이 여전히 있는지 확인한다. 바뀌었으면 STOP 후 재측정.

- [ ] **AC-2 (bite)** — 도입한 가드가 실제로 문다: 통합 모듈 하나의 태그 필터를 일부러

      확인하고 되돌린다. 🔴 **이 bite 가 이 티켓의 전부다.**
- [ ] **AC-3 (초록 회차에서 네 값을 읽을 수 있다)** — 수정 후 **성공한** 통합 잡에서
      네 값을 실제로 읽어 적는다. 🔴 `MONO-542` 가 하지 못했던 바로 그 일이다.
- [ ] **AC-4 (형제 전수)** — `.github/workflows/` 전체에서 조건부 리포트 업로드를 전수로
      센다. 같은 공백이 있는 다른 잡을 나열하고 이 티켓에서 고칠지 별건으로 뺄지 정한다.
      **0건이면 0건이라고 적는다.**
- [ ] **AC-5 (틀린 기록 정정)** — `tasks/done/TASK-MONO-541-…` 과 root `tasks/INDEX.md` 의
      *"그 이름의 아티팩트가 1차 시도분 하나뿐이라 재실행이 새로 올리지 않았다"* 서술을
      정확한 사유(**성공 회차는 업로드 조건 때문에 아무것도 올리지 않는다**)로 고친다.
      🔴 **한 사실이 두 곳에 있으면 한쪽만 고쳐진다** — 두 곳을 함께 고칠 것.

# Edge Cases

- `if: always()` 는 **취소된 잡에서도** 업로드를 시도한다. `if: '!cancelled()'` 가 더 맞을
  수 있다 — 어느 쪽인지 정하고 이유를 적을 것.
- 🔴 **`upload-artifact@v4` 는 같은 이름의 중복 업로드를 거부한다.** (a)를 고르면
  **재실행 경로를 반드시 실측할 것** — 재실행이 업로드에 실패하면 여전히 낡은 아티팩트를
  재게 되고, 그것은 `MONO-541` 이 본 증상과 **구별되지 않는다**.
- (b)를 고르면 **의도적으로 비어 있는 스위트**가 있는지 먼저 확인해야 한다 — 있으면 그
  모듈이 즉시 빨개진다.

# Failure Scenarios

- **`if: always()` 로 바꾸고 끝낸다** → 재실행 시 이름 충돌로 업로드가 실패해 **여전히
  낡은 아티팩트를 잰다**.
- **bite 없이 닫는다** → 0-발견이 조용히 통과하는지 알 수 없다.
- **AC-5 를 건너뛴다** → `MONO-541` 의 틀린 사유가 남아 다음 사람이 `gh` 의 재시도 동작을
  의심하며 시간을 쓴다.
