# 🟢 AC-0 정정 — ⚪ 가 닫혔다. **attempt 를 열면 잴 수 있었다** (2026-09-18 UTC · 분석=Opus 5)

2026-09-17 기록은 CI 이력 경로를 이렇게 닫았다:

> 🔴🔴 **그 0 은 거짓이다** — 우리가 본 실패는 **실패 잡만 재실행**해서 결론이 `success` 로 덮였고,
> `gh run list`/`run view` 는 **마지막 시도만** 본다. ⇒ 이 질의는 재실행된 flake 를
> **구조적으로 과소계수**한다

🔵 **진단은 정확했다. 그런데 결론이 한 발 짧았다** — 과소계수하는 것은 *그 질의*이지 *API* 가
아니다. GitHub 는 시도를 **주소로 갖고 있다**: `…/actions/runs/<id>/attempts/<n>/jobs`.
그리고 `runs` 목록은 각 런의 `run_attempt` 를 **이미 실어 준다** ⇒ **재실행된 런만 골라
그 이전 시도를 열면** 덮인 실패가 전부 나온다.

이 티켓이 AC-3 에서 이미 배운 구별(«런» ≠ «실행»)이 분모에도 똑같이 적용된다.

## ⇒ 빈도 (수정 전/후를 **갈라서**)

🔵 **이 티켓이 「고쳤다」고 말할 수 있는 근거는 통계가 아니라 AC-2 의 구조 변경과 bite 다**:

«그 모양이 가능한 구조» 자체를 없앴고, 옛 제품 코드로 되돌리면 그 칸이 **여전히 빨개진다**는 것을
확인했다. 🔴 빈도 측정은 그 판단을 **대체하지 않는다** — 뒷받침할 검정력이 애초에 없다.

  함정). 위 방법은 `gh api` 의 workflow-runs 엔드포인트를 쓴다.
- 🔴 **런 목록이 최신순으로 오지 않을 수 있다** — `per_page` 가 작으면 **옛 런이 맨 위에 얹힌다**
  (실제로 밟았다: `per_page=20` 이 2026-09-10~12 런을 냈다). `created=>=<날짜>` 필터를 걸어라.

## 🔵 다음 사람이 그대로 쓸 수 있는 형태

```bash
WF=262981827   # "CI" (repos/<r>/actions/workflows 에서 id 확인 — 이름이 같은 게 여럿일 수 있다)
# 1) 창 안의 런 + 시도 수
gh api "repos/kanggle/monorepo-lab/actions/workflows/$WF/runs?branch=main&per_page=100&created=%3E%3D2026-09-01" \
  --jq '.workflow_runs[]|select(.run_attempt>1)|"\(.head_sha[0:9])\t\(.id)\tatt=\(.run_attempt)"'
# 2) 덮인 시도를 직접 연다
gh api "repos/kanggle/monorepo-lab/actions/runs/<id>/attempts/1/jobs?per_page=100" \
  --jq '.jobs[]|select(.name|startswith("<job name>"))|.conclusion'
# 3) 분모: skipped 를 빼고 «실행» 만 센다
```

# 🟢 AC-1 — 원인: ⚪ 를 **유지한다**(승격하지 않는다)

🔴 위 빈도 측정은 **원인을 지목하지 못한다.** 재현이 여전히 없고(이 호스트에서 저장소 러너가
기동 불가 — AC-0 의 첫 표), 창 안의 실패는 **1건**이라 대조군을 세울 표본이 아니다.

🔵 그래서 2026-09-17 의 판단을 그대로 둔다: *«원인» 이 아니라 «그 모양이 가능한 구조» 를 고쳤다.*
🔴 **이것을 「원인 지목」으로 올려 적지 않는다** — 실패 메시지 해석(첫 호출에서 모킹이 안 먹어 진짜
클라이언트가 렌더됐다)은 **가장 그럴듯한 설명**이지 관측이 아니고, 이 저장소는 그 승격으로 여러 번
대가를 치렀다.

# 🟢 AC-3 — **닫힘.** 실행 **12회**, 같은 칸 실패 **0**

2026-09-18 정정이 «5런» 을 **«실행 5회»** 로 다시 읽었고, 그때는 **2/5** 였다. 지금 다시 세니:

그것보다 강하게 읽지 않는다.

# ⚪ AC-1 의 처분 — **지목 못 한 채로 닫는다.** 티켓이 이 경우를 미리 승인해 뒀다

AC-1 은 *"원인을 **관측으로** 지목. 🔴 «모킹 순서 때문일 것» 은 판정이 아니다"* 를 요구한다.
**지목하지 못했고, 앞으로도 이 호스트에서는 못 한다.** 그 사실과 이유를 여기 못박고 닫는다.

**왜 못 하나 (둘 다 구조적이다):**

1. **재현 경로가 없다.** 저장소 러너(vitest 4)가 이 호스트의 Node 24 에서
   `ERR_PACKAGE_IMPORT_NOT_DEFINED` 로 **기동조차 못 한다**(nvm·fnm·volta 없음). 러너를 바꿔
   돌린 30회는 **다른 러너의 빈도**라 CI 의 빈도가 아니다.
2. **표본이 1건이다.** § AC-0 의 attempt 전수가 창 안의 실패를 **정확히 1건**으로 확정했다.
   🔴 대조군(단독 실행 / 파일 전체 / 병렬 끔)은 **재현 가능한 실패**를 전제로 하는 설계다 —
   1건으로는 어떤 대조군도 신호를 못 만든다.

**티켓이 이 갈래를 이미 적어 뒀다** — § Edge Cases:

> | 원인이 러너 버전 | 그 사실을 적고 **범위를 나눈다**(이 티켓은 이 파일까지) |

⇒ 그대로 한다. 이 티켓의 산출물은 **«이 파일의 하네스를 결정적으로 만든 것»**(AC-2)이고,
«무엇이 그 한 번을 일으켰는가» 는 **미지로 남는다**.

🔴 **그러므로 이 티켓은 「flake 를 고쳤다」고 주장하지 않는다.** 주장하는 것은 정확히 둘이다:
① 실행 중 `resetModules`+`doMock` 이 오가던 **구조를 없앴다**(호이스팅 `vi.mock` + 정적 import),
② 그 변경이 **bite 를 죽이지 않았다**(옛 제품 코드로 되돌리면 여전히 빨갛다). § AC-0 의 산술이
보여 주듯 수정 후 12연속 초록은 ①의 효력을 **증명하지 않는다**.

**다시 열릴 조건 (날짜가 아니라 사건이다):** 같은 칸이 CI 에서 **한 번 더** 빨개지면 그것이
**두 번째 표본**이고, 그때 비로소 대조군을 세울 수 있다. 🔵 그때 쓸 도구는 § AC-0 에 적어 둔
attempt 전수 방법이다 — `gh run list` 가 아니라 `gh api …/attempts/<n>/jobs`.
