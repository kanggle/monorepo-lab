# Context — 이관은 배포를 2배로 만든다 (2026-08-23 실측)

지금 `vercel.json` 은 **2개**다:

```
infra/demo/aws/site/vercel.json                              → kanggle-portfolio
projects/fan-platform/web/fan-platform-web/vercel.json       → kanggle-fan
```

단계 2·3 은 web-store 와 console 에 각각 **새 Vercel 프로젝트**를 만든다 ⇒ **2 → 4**.
`scripts/vercel-should-build.sh` 의 헤더가 왜 그게 문제인지 이미 적어 뒀다:

> 이 저장소는 Vercel 프로젝트가 **둘**이라 커밋 하나가 배포 **둘**을 굽고, 문서 전용 PR 도
> 예외가 아니었다 ⇒ 무료 플랜의 일일 한도에 닿아 24시간 동안 모든 PR 이 빨개지고,
> 그동안 **론처는 낡은 판을 계속 서빙했다.**

프로젝트 2개로도 그 한도에 닿았다. **2026-08-23 하루에만 두 번 물렸다**(06:12Z 이후 24시간
차단). 4개면 같은 커밋 흐름에 배포 압력이 **2배**가 된다.

🔵 `ignoreCommand` 가 그걸 줄이도록 설계돼 있지만, **`TASK-MONO-572` 가 그 판정 창이 한 커밋뿐임을
밝혔다** — 여러 커밋 push 에서는 판정이 빗나간다. 즉 **완화 장치 자체가 지금 새는 중**이다.

# Acceptance Criteria

## AC-0 — 한도를 **문서가 아니라 계정에서** 확인한다

Vercel 무료(Hobby) 플랜의 실제 한도 4종을 **이 계정의 사용량 화면에서** 읽는다:

| 축 | 왜 |
|---|---|
| 일일 배포 수 | 오늘 두 번 물린 축 |
| 함수 호출 수 | (B) 는 **모든 데모 트래픽**을 함수로 보낸다 |
| 함수 실행 시간 | 프록시 한 홉이 늘어난다 |
| 대역폭 | 이미지·정적 자산 포함 |

🔴 **문서 값을 적지 마라.** 플랜 한도는 바뀌고, 계정에 적용된 값이 진실이다.
🔴 이 단계는 **소유자 대시보드 작업**이다 — 이 저장소에 Vercel 토큰·CLI 가 없다(실측).

### 🔴🔴 AC-0 추가 항목 (AC-1 실측이 만들어낸 것)

> **`Canceled by Ignored Build Step` 이 일일 배포 한도를 소비하는가?**

한도 숫자보다 **이 답이 판정을 뒤집는다.** AC-1 이 관측한 것: 건너뛴 커밋도 **`pending` 을
거친다**(Vercel 이 배포를 만들었다가 취소) — 즉 `ignoreCommand` 가 확실히 아끼는 것은
**빌드 시간**이고, **배포 건수**까지 아끼는지는 **아직 모른다**.

- **먹는다면** → `ignoreCommand` 를 아무리 촘촘히 해도 프로젝트 4개는 이벤트가 **그대로 2배**다.
  `TASK-MONO-562` 완화책의 전제가 절반만 참이었다는 뜻이기도 하다.
- **안 먹는다면** → AC-1 의 하한이 실제보다 많이 낮았다는 뜻이고, 누락분(닫힌 PR·force-push·
  재실행)을 다시 세야 한다.

🔵 대시보드의 사용량 그래프에서 **rate limit 이 걸린 날의 배포 건수**를 읽으면 갈린다 —
AC-1 의 하한(08-22 = 72)보다 크게 높으면 「먹는다」 쪽이다.

### 🔵 같은 방문에서 함께 볼 것 (2026-08-25, `TASK-MONO-577` AC-1.5)

대시보드를 여는 김에 **AWS 쪽 한 줄**도 확인해 달라 — 다른 티켓의 결정이 이 숫자에 걸려 있다.

> **고정 공인 IPv4(Elastic IP)를 이 데모에 붙이면 월 얼마인가?**

왜 여기 붙였나: `TASK-MONO-577` 이 *"주소가 안 바뀌면 해석기 자체가 필요 없다"* 를 선택지 D 로
올렸는데, 그 대가가 **월 과금**이고 데모는 예산상 **한 달의 약 1.4%** 만 켜져 있다(600분/월).
즉 대부분의 시간이 **유휴**다.

🔴 **금액을 추정해서 적지 마라.** AWS 의 퍼블릭 IPv4 과금은 정책이 바뀌었고 *"유휴 EIP 만
과금"* 이라는 옛 상식은 더 이상 정확하지 않을 수 있다. **계정 값이 진실이다** — 이 티켓 AC-0 의
원칙과 같다.

## AC-1 — 배포 건수를 **실제 커밋 흐름으로** 추정한다

최근 30일의 `main` 커밋 수와 PR 수를 세고, 프로젝트당 `ignoreCommand` 통과율을 곱한다.

```bash
git log --since=30.days --oneline origin/main | wc -l
gh pr list --state merged --limit 100 --json mergedAt --jq '[.[]|select(.mergedAt>"...")]|length'
```

🔴 **추정치임을 명시한다.** 이것은 *"앞으로 이만큼 구울 것"* 의 산술이지 측정이 아니다.
[[feedback_local_proves_behaviour_not_performance]]

🔵 **대조군**: 같은 창에서 실제로 몇 건이 구워졌는지도 센다(커밋 상태 API 의 Vercel context
개수). 산술과 실측이 어긋나면 **`ignoreCommand` 의 통과율 가정이 틀린 것**이고, 그 자체가 발견이다.

## AC-2 — 4개 프로젝트에서 한도를 넘는지 판정한다

AC-0 의 한도 ÷ AC-1 의 추정 배포량. **넘으면 이관 순서와 속도가 바뀐다.**

판정은 셋 중 하나로 적는다:

- **견딘다** — 근거 숫자와 여유율.
- **못 견딘다** — 그러면 선택지는 ① 유료 플랜 ② 프로젝트 수를 늘리지 않는 다른 배치
  ③ `ignoreCommand` 를 더 촘촘하게(단, `TASK-MONO-572` 가 먼저) 중 하나이고, **이 티켓은
  고르지 않는다** — `ADR-MONO-067` 의 후속 결정 입력이다.
- **판정 불가** — 어느 입력이 없어서인지 적는다.

## AC-3 — `TASK-MONO-572` 와의 순서를 명시한다

572 가 고쳐지기 전에는 `ignoreCommand` 통과율이 **실제보다 높게** 측정된다(빗나간 판정이
"건너뜀"으로 집계되므로). 572 이후에 재는 것이 정확하고, 그 전에 잰다면 **그 사실을 숫자 옆에
적는다**.

## AC-4 — 결과를 `ADR-MONO-067` § AC-0 4번에 기록한다

프로젝트 2 → 4 라는 사실도 함께 적는다. ADR 본문은 그 축을 세지 않았다.

# ✅ AC-1 실측 (2026-08-23 UTC)

## 🔴 먼저: 첫 계측기가 틀렸다 — Deployments API 로는 못 잰다

`repos/…/deployments` 로 세려 했다. **두 가지가 무효였다.**

**① 창이 30일이 아니라 4일이다.** 전체 페이지네이션이 **49건**을 주고 가장 오래된 것이
`2026-08-19` 다. 30일 창을 물어놓고 4일짜리 계측기를 쓴 셈이고, 그 경계는 **질문이 아니라
계측기가 정한 것**이다. [[feedback_recount_population_dont_inherit_scope]]

**② 소비를 못 센다.** 최근 main 커밋 12개를 하나씩 열어 보니 **전부 `deployments=0`** 인데,
그중 8개는 Vercel 상태가 **`pending` → `success` (`Canceled by Ignored Build Step`)** 였다.
즉 **Vercel 은 배포를 만들었다가 취소했고, Deployments API 에는 아무 흔적이 없다.**

⇒ 완료된 배포만 세는 계측기로 **할당량 소비를 판정할 수 없다**. 소비의 단위는 완료가 아니라
**`pending` 이 붙은 사건**이다.

🔵 부수 확인: rate-limit 실패 5건은 **전부 `pending` 없는 단발 failure** 였다. 판별자가 또 맞았다.

## 실측한 것 — 커밋 흐름

| 축 | 값 |
|---|---|
| `origin/main` 커밋 / 30일 | **469** (≈15.6/일) |
| 머지된 PR / 30일 | **513** (≈17/일) |

## 배포 트리거 이벤트 — 하루 단위

`pending` 이 붙는 사건 ≈ (PR 커밋 + main 커밋) × **프로젝트 수**.

| 날짜 | 머지 PR | PR 커밋 | main 커밋 | **이벤트(프로젝트 2)** | **프로젝트 4 환산** |
|---|---:|---:|---:|---:|---:|
| 2026-08-21 | 7 | 16 | 7 | **46** | 92 |
| 2026-08-22 | 15 | 21 | 15 | **72** | 144 |
| 2026-08-23 | 10 | 15 | 10 | **50** | 100 |

## 🔴 이 숫자는 **하한**이다 — 세 가지를 못 셌다

1. **머지된 PR 만** 셌다. 닫힌·열린 PR 의 push 는 빠졌다.
2. `gh pr view --json commits` 는 **살아남은 커밋**을 준다. rebase·amend·force-push 로 갈린
   head 커밋들은 각각 배포를 텄는데 목록엔 없다.
3. 재실행·수동 배포는 셈 밖이다.

⇒ 실제 이벤트는 위 표보다 **크다**. 08-22 의 72 는 «최소 72» 로 읽어야 한다.

## 🔴🔴 그래서 AC-0 의 질문이 바뀐다

08-22·08-23 에 **실제로 rate limit 에 걸렸다**. 그런데 위 하한은 72·50 이다.
두 사실을 잇는 설명은 둘 중 하나뿐이다:

| 가설 | 뜻 |
|---|---|
| **A. 건너뛴 빌드도 한도를 먹는다** | `ignoreCommand` 는 **빌드 시간**만 아끼고 **배포 건수**는 못 줄인다 ⇒ `TASK-MONO-562` 완화책의 전제가 절반만 참이다 |
| **B. 하한이 실제보다 많이 낮다** | 위 ①②③ 의 누락분이 커서 실제 이벤트가 한도를 넘었다 |

**둘 다일 수도 있다.** 어느 쪽이냐가 이관 가능 여부를 가르므로, **AC-0 은 「한도가 얼마인가」에
더해 「Canceled by Ignored Build Step 이 한도를 소비하는가」를 반드시 확인해야 한다.**
그것 없이는 AC-2 를 판정할 수 없다.

🔵 **A 가 참이면 방향은 이미 정해진다** — 프로젝트를 4개로 늘리면 `ignoreCommand` 를 아무리
촘촘히 해도 **이벤트 수가 그대로 2배**가 된다. 그 경우 선택지는 유료 플랜이거나, 프로젝트 수를
늘리지 않는 배치다.

## AC-3 준수 — 572 이전에 잰 숫자다

`TASK-MONO-572`(무시 판정 창이 한 커밋)가 아직 안 고쳐졌다. 그 결함은 **빌드를 더 굽는 쪽이
아니라 덜 굽는 쪽**으로 작동하므로, 위 이벤트 수에는 영향이 없다(어차피 `pending` 은 붙는다).
🔵 다만 «통과율» 을 계산하려 했다면 그 숫자는 오염됐을 것이다 — 그래서 통과율 대신 **이벤트 수**로
잰 것이다.

# ✅ AC-0 완료 (2026-08-27 UTC) — **A 가 참이다. 건너뛴 빌드도 한도를 먹는다.**

## 어떻게 쟀나 — 대시보드가 아니라 **커밋 상태 이력**으로

🔴 **일일 배포 수는 사용량 화면에 막대가 없다.** 소유자가 08-26 에 화면 전체를 붙여넣었을 때
함수·대역폭 축은 읽혔지만(→ `TASK-MONO-587` § ③), 이 축은 **사용량 항목이 아니라 롤링
rate limiter** 라 거기서 읽히지 않는다. 그래서 **행위로** 쟀다.

모집단 = rate limit 이 처음 문 순간(**2026-08-26T08:30:51Z**) 직전 **롤링 24시간**의
모든 커밋 상태 이벤트. 출처 둘: `origin/main` 커밋 + 그 창에 머지된 PR 18건의 브랜치 커밋.

```
repos/:owner/:repo/commits/<sha>/status  →  context, state, description, updated_at
```

## 실측 — 창 안의 배포 이벤트 (2026-08-25T08:30Z ~ 2026-08-26T08:31Z)

| | `kanggle-fan` | `kanggle-portfolio` | **합** |
|---|---:|---:|---:|
| `Canceled by Ignored Build Step` (건너뜀) | 35 | 34 | **69** |
| `Deployment has completed` (실제 빌드) | 2 | 3 | **5** |
| **생성된 배포** | **37** | **37** | **74** |
| `rate limited` (배포가 **안 만들어짐**) | 2 | 2 | 4 |

출처별로는 **main 34건 · PR 브랜치 40건**(생성분 기준).

## 🔴🔴 판정 ① — **건너뛴 배포는 한도를 소비한다** (가설 **A**)

24시간에 **실제 빌드는 5건**이었다. 한도는 100/일이다.
**5건으로는 100 한도에 닿을 수 없다.** 그런데 닿았다.

⇒ `ignoreCommand` 가 아끼는 것은 **빌드 시간뿐**이고, **배포 건수는 하나도 못 아낀다.**
`TASK-MONO-562` 완화책의 전제는 **절반만 참이었다.**

컨테이너 안에서 돈다. **건너뛴 빌드는 «만들어진 배포» 다.** 산술과 기전이 같은 답을 준다.
