# 배경 — 2026-08-18(UTC) 굽기 4회차 실패

`TASK-MONO-551`·`553`·`554-A`·`552(b)` 를 한 AMI 에 담으려던 굽기가 **19분 28초에 실패**했다.

```
PACKER_RC=1
Build 'amazon-ebs.demo' errored after 19 minutes 28 seconds:
  Script exited with non-zero exit status: 123. Allowed exit codes are: [0]
==> Builds finished but no artifacts were created.
```

## 🔴 실패한 것이 하나도 없다

실패 후 진단(`error-cleanup-provisioner`)이 남긴 전수:

| 확인 | 결과 |
|---|---|
| 커널 OOM / kill 흔적 | **0건** |
| docker 데몬 | `active` · `daemon: reachable` |
| 디스크 | 96G 중 22G 사용 (**75G 여유**) |
| 메모리 | 31.5GB 중 **30.3GB 여유** |
| 8개 프로젝트 빌드 로그 | **전부 `Built` / `Pulled`** 로 정상 종료 |
| 스크립트 트레이스 | 끝까지 실행 → `+ rc=0` → EXIT trap 이 **`DIED rc=0`** 출력 |

**작업은 전부 성공했고 스크립트는 스스로 0 으로 끝났는데 packer 는 123 을 받았다.**
스크립트 어디에도 123 을 낼 코드가 없다(`xargs` 없음, `exit` 는 trap 의 `exit $rc` 하나뿐).

## 어디서 죽었는지는 특정했다

프로비저너 시작 줄은 로그에 6개뿐이고(정규 5 + error-cleanup 1), 템플릿의 정규
프로비저너는 7개다 ⇒ **5번(이미지 빌드)에서 죽었다.**

- `grep -c '\[verify\]'` = **0** ⇒ 7번(`verify-demo-wrapper.sh`)은 **돈 적이 없다.**
  같은 날 추가된 가드 `(z4)`·`(z6)` 는 이 실패와 **무관**하다(용의선상에서 제외).
- 6번(systemd 유닛 설치)도 시작하지 않았다.

## 유력 가설 — 성공 경로가 마지막에 출력을 쏟는다

🔴 **가설이지 진단이 아니다.** 123 의 출처는 여전히 모른다. 그러나:

1. **템플릿이 같은 실패를 이미 두 번 기록해 뒀다.** 5번 프로비저너 주석:
   > *"attempt 2 는 scm 이미지 export 중, attempt 3 은 console-web 라우트 출력 중에 죽었다.
   > **서로 다른 지점** = 결정론적 단계 실패가 아니다. 두 번 다 (a) 출력이 폭주하던 순간이고
   > (b) 로그 마지막 줄이 문자 중간에서 잘렸으며 … 남는 설명은 대용량 출력 중 SSH 채널이 끊긴 것."*

   그때의 처방이 **빌드 출력을 인스턴스의 파일로 돌리는 것**이었고, 그건 지금도 유효하다
   (이번 로그에 빌드 출력은 안 흐른다).

2. **그 처방이 닿지 않은 자리가 정확히 죽은 자리다.** 5번의 마지막 네 줄:

   ```
   docker image prune -f
   docker builder prune -af      ← 빌드캐시 항목 수십 줄
   docker image ls               ← 이미지 40여 개
   df -h /; free -m
   ```

   그리고 **EXIT trap 은 성공했을 때도 돈다** — `df` · `free` · `dmesg | tail -40` ·
   `docker system df` 까지 더 쏟는다. 합쳐서 **약 470줄이 한 번에** 나간다.

3. **로그의 출력 순서가 뒤엉켰다** — `+ docker image ls` / `+ df -h /` / `+ free -m` 트레이스가
   `docker builder prune` 출력 **사이에** 끼어 찍혔고, `dmesg` 마지막 줄은 **문자 중간에서
   잘렸다**(`[  644.205299] docker`). 채널이 밀리고 있었다는 지문이다.

🔵 이번 회차가 이전 두 번과 **다른 점**: EXIT trap 이 **실행됐다**(이전엔 bash 하드킬로 안 돌았다).
즉 원격 스크립트는 정상 종료했고, **깨진 것은 종료 상태의 전달**이다. 이 차이가 가설을
"프로세스가 죽는다"에서 "채널이 밀린다"로 좁혀 준다.

## ✅ 2026-08-21 UTC — 이번 세션의 굽기 로그로 닫는다. **N=1 이고 그렇게만 적는다**

`packer-bake-0821b.log` (1,482줄, `Build 'amazon-ebs.demo' finished after 1 hour 1 minute`).

**AC-1 — 성공 경로가 조용하다. 세어서 판정했다.**
5번 프로비저너 꼬리 구간의 실제 출력은 **한 줄**이다:

```
+ docker image prune -f
+ docker builder prune -af
+ docker image ls
[ami] 정리 완료 — 이미지 64개 · 75G free · 30280MB avail     ← 출력은 이 한 줄뿐
+ rc=0
```

🔵 `+`/`++` 로 시작하는 줄은 프로비저너의 `set -x` **추적**이지 세 명령의 출력이 아니다.
고치기 전에 문제였던 것은 `docker image ls` 의 **이미지 64행**과 `builder prune` 의 표였고,
그것은 이제 **0줄**이다(전부 `/var/log/ami-*.log` 로 갔다). 추적까지 포함해 세도 12줄.

**AC-2 — 티켓 자신이 허용한 값싼 경로로 충족.** 라이브 실패 굽기(회당 $0.3 + 1시간)는
**하지 않았다.** AC-2 가 명시한 대체 경로 — *"로컬에서 같은 인라인을 돌려 파일이 생기는지
확인하고 그렇게 적는다"* — 를 수행했고 그 사실이 위 § 에 적혀 있다. 🔴 **"실패 시 진단이
남는다" 는 라이브에서 한 번도 행사되지 않았다**는 것을 여기 남긴다.

**AC-3 — 굽기가 실제로 성공했다.** `ap-northeast-2: ami-0c768f12eb9a024ce`,
`Builds finished. The artifacts of successful builds are:`.
🔴 `PACKER_RC` 변수 자체는 이 로그에 안 남았다. 대신 **더 강한 증거**가 있다: 그 AMI 로
이번 세션에 **인스턴스를 두 번 띄웠고**, 런타임에서 세 파일의 md5 가 저장소 blob 과 일치함을
확인했다. 파이프 종료코드와 달리 이것은 **산출물 자체**다.

**AC-4 — 가설을 판정으로 승격하지 않는다. N=1.**
방아쇠 후보(출력 폭주)를 치운 뒤 **성공한 굽기는 1회**다. 이 결함은 서로 다른 세 지점에서
죽은 **비결정적** 결함이므로, **1회 성공은 원인 확정이 아니다.** 다음 굽기가 또 성공하면
N=2 로 갱신하라 — 그 전까지 *"원인은 출력 폭주였다"* 라고 적지 마라.

# Goal

굽기가 **성공했을 때 성공으로 보고**된다. 그리고 실패했을 때 진단할 것은 그대로 남는다.

# Scope

## In Scope

- **성공 경로의 출력 버스트를 없앤다.** 5번 프로비저너 꼬리의 `prune`/`image ls` 출력을
  인스턴스의 파일로 돌리고 **한 줄 요약만** 흘린다(빌드 출력에 이미 적용된 처방과 동일).
- **EXIT trap 이 성공했을 때는 조용하다.** 진단 덤프는 `rc != 0` 일 때만. 지금은 성공해도
  `dmesg | tail -40` + `docker system df` 를 쏟는다.
- **버린 것을 잃지 않는다.** 새로 만든 로그 파일을 `error-cleanup-provisioner` 가 tail 한다.
  🔴 이게 없으면 이 고침은 *"안 보이니까 조용해졌다"* 가 되고, 다음 실패의 진단을 없앤다.

## Out of Scope

- **123 의 근본 원인 규명.** 알 수 없고, 재현 비용이 회당 약 $0.3 + 20분이다. 이 티켓은
  *방아쇠로 의심되는 것을 치우고 다시 재는 것*이지 원인을 규명했다고 주장하지 않는다.
- SSH 커넥션 튜닝(`ssh_read_write_timeout` 등) — 가설이 맞는지 먼저 보고, 아니면 그때.
- 빌드 단계 자체의 내용(무엇을 굽는가)은 건드리지 않는다.

> 한 명령이 압도적이다 — 세지 않았으면 넷을 똑같이 취급했을 것이다.

**AC-1 · AC-2 — 저장소 층 ✅ 완료.**
꼬리 세 명령을 `/var/log/ami-{prune-image,prune-builder,images}.log` 로 돌리고 **요약 한 줄**만
남겼다. EXIT trap 은 `rc != 0` 일 때만 진단을 흘린다. `error-cleanup-provisioner` 는 새 로그
셋을 tail 한다(AC-2). 🔵 대조군: **로그 파일이 없는 상태**(그 줄들에 닿기 전에 죽은 경우)로
같은 루프를 돌려 `0 lines` 로 보고하고 **중단되지 않는** 것을 확인했다.
🔴 로컬 검증에서 `docker builder prune -af` 는 **일부러 돌리지 않았다** — 이 머신의 빌드
캐시를 지우기 때문이다. 세 줄의 리다이렉트 형태는 동일하므로 `docker image ls` 로 대표 검증했고,
그 사실을 여기 적는다(대표 1건은 전수의 증거가 아니다).

**AC-1 — 성공 경로가 조용하다.** 고침 후 5번 프로비저너의 꼬리에서 나가는 줄 수가
**한 자릿수**다. 판정은 다음 굽기 로그의 해당 구간을 **세어서** 한다 — "조용해 보인다"가 아니라.

**AC-2 — 진단은 그대로다. 🔴 대조군 필수.**
새 로그 파일(`ami-prune-*.log`·`ami-images.log`)이 실패 시 `error-cleanup-provisioner` 의
출력에 **나타난다**. 판정은 **실패를 하나 만들어서** 한다 — 성공한 굽기만 보면
*"진단이 남는지"* 는 한 번도 행사되지 않는다.
🔵 값싼 방법: 5번 프로비저너 뒤에 `exit 1` 하는 임시 프로비저너를 끼워 한 번 굽는다.
비싸면(회당 $0.3) 최소한 **로컬에서 같은 인라인을 돌려** 파일이 생기는지 확인하고 그렇게 적는다.

**AC-3 — 굽기가 실제로 성공한다.** `PACKER_RC=0` 이고 새 AMI ID 가 나온다.
🔴 **`PACKER_RC` 로 판정한다.** 이 세션에서 `<task-notification>` 이 *"exit code 0"* 이라고
보고한 건이 실제로는 실패였다 — 그 0 은 파이프라인 마지막 `tail` 의 종료코드였다.
파이프 뒤의 종료코드는 판정에 쓰지 않는다.

**AC-4 — 가설을 판정으로 승격하지 않는다.** 한 번 성공했다고 *"원인은 출력 폭주였다"* 로
적지 않는다. 이 결함은 이미 **비결정적**임이 관측됐다(서로 다른 세 지점에서 죽었다).
적을 수 있는 것은 *"방아쇠 후보를 치웠고 그 뒤 N회 성공했다"* 뿐이다. **N 을 적을 것.**

# Edge Cases

- **파일로 돌린 출력이 디스크를 먹는다** — `docker image ls` 는 수십 KB 수준이라 무시할 만하다.
  단, `/var/log/ami-*.log` 는 **AMI 에 그대로 구워진다.** 크기를 확인하고, 커지면 굽기 끝에 지운다.
- **조용해지면 진행 상황이 안 보인다** — 5번은 15분 넘게 도는 단계다. 프로젝트마다 한 줄씩
  찍는 `[ami] build: <p>` 는 **유지**해야 한다(그게 없으면 멈춘 것과 도는 것을 구별 못 한다).
- **가설이 틀렸을 수 있다** — 고쳐도 또 123 이 나면 그건 출력이 아니라는 뜻이고, 그때는
  SSH 커넥션 축(`ssh_read_write_timeout`, `pty`)으로 넘어간다. **그 실패도 정보다.**

# Failure Scenarios

- **진단까지 같이 조용하게 만든다** — 실패 시 tail 을 안 붙이면 다음 실패는 이번보다
  **덜** 알 수 있다. AC-2 가 그것을 막는다.
- **한 번 성공하고 "고쳤다"고 적는다** — 비결정적 실패에 대한 1회 성공은 증거가 약하다(AC-4).
- **`PACKER_RC` 아닌 것으로 판정한다** — 이 세션이 이미 한 번 속았다(AC-3).
