**AC-2 — 규칙이 저장소에 있다.**
무시 조건이 대시보드에만 있으면 다음 사람은 그것을 볼 수 없고, 이 티켓의 판정도 재현 불가다.
저장소 파일로 표현하고, 그 파일이 **어느 Vercel 프로젝트의 Root Directory 에 속하는지** 주석으로 적는다.
⚠️ `vercel.json` 은 **스키마가 엄격해 모르는 최상위 키를 거부**한다 — 설명을 `"//key"` 로 끼워 넣지 마라.
`TASK-MONO-557` 이 정확히 그것으로 배포를 깼다(`45bdca743` 성공 → `ea9d5e79c`·`2679b8e41` 연속 실패).
설명의 집은 `build.sh` 다.

**AC-3 — 론처가 낡았다는 사실이 보인다. 🔴 이 AC 가 이 티켓의 핵심이다.**
rate limit 이든 다른 이유든 **배포가 실패한 채 사이트가 옛 판을 서빙하는 상태**를 판정할 수 있어야 한다.
최소한: 배포된 페이지가 **자기가 어느 커밋에서 나왔는지** 말할 수 있어야 한다
(예: `config.js` 나 메타 태그에 빌드 커밋 SHA — `build.sh` 가 이미 `config.js` 를 생성하므로 자리는 있다).

🔴 **판정은 URL 200 이 아니다.** 200 은 낡은 판도 낸다 — 그것이 MONO-557 이 이름 붙인 함정이다.
판정은 **서빙 중인 SHA 가 `origin/main` 의 그것과 같은가** 로 한다.
🔴 **대조군**: 일부러 옛 판을 가리키게 만들었을 때 그 판정이 **다르다고 말하는지** 확인한다
(같은 값끼리 비교하면 언제나 통과한다).

**AC-4 — 선택지를 숫자와 함께 제시한다 (실행하지 않는다).**
AC-0 의 실측을 근거로, 남는 위험과 완화안을 **소유자가 고를 수 있는 형태**로 적는다:
프리뷰 배포 끄기 / 프로젝트 통합 / 유료 전환(월 비용) 등. 각 안의 **잃는 것**을 반드시 같이 적는다 —
특히 프리뷰 배포를 끄면 **머지 전에 론처가 깨진 것을 볼 기회**가 사라진다.

**가드 `scripts/check-vercel-build-triggers.sh`** — 러너 = ci.yml 잡 `vercel-build-triggers`
(경로 필터는 `code-changed` 와 **AND 하지 않는다**: 이 드리프트의 도착 경로 셋이 전부 비-코드다).

🔴 **모집단을 하드코딩하지 않는다.** `git ls-files '*vercel.json'` 로 전수 발견하고 **하한 2**
(provenance: 2026-08-21 = portfolio + fan). 세 번째 Vercel 프로젝트가 생기면 이 가드가 본다.
하드코딩한 모집단은 대상이 사라져도 자기가 적어둔 것을 계속 테스트하고 통과한다.

발견한 설정마다 **임시 git 저장소를 만들어 판정자를 실제로 돌리고 종료코드를 읽는다** — grep 이 아니다
(문자열 검사는 **잘 문서화할수록 더 확실히 초록**이 된다):

| 칸 | 상황 | 기대 | 실측 |
|---|---|---|---|
| (1) | 자기 경로가 바뀐 커밋 | 빌드 (rc=1) | ✅ 두 프로젝트 모두 |
| (2) | `tasks/` 만 바뀐 커밋 | 건너뜀 (rc=0) | ✅ 두 프로젝트 모두 |
| (3) | 부모 커밋 없음 | 빌드 (fail-open) | ✅ 두 프로젝트 모두 |
| (4) | pathspec 추출 0건 | **가드 실패** | ✅ (아래 bite (d)) |

**bite — 진짜 설정의 사본을 망가뜨려 4/4 발화**: (a) `ignoreCommand` 제거 · (b) 주석 키 삽입 ·
(c) 설정 1개 삭제(하한 위반) · (d) pathspec 모양 변경(추출 0건). 무망가 사본은 통과(rc=0).
🔵 (c) 는 **작성 중에 실제로 물었다** — 새 `vercel.json` 이 아직 untracked 라 `git ls-files` 가 1개만 봤다.

## 🔴🔴 AC-3 을 만들다 옆에서 나온 형제 결함 — **배포 두 경로가 같은 커밋에서 다른 바이트를 서빙한다**

신선도 판정자를 처음 돌렸더니 **두 오리진이 다 "낡음"** 이었다. CloudFront 는 방금 apply 한 판이라
신선해야 했다 ⇒ **대조군이 어긋났고, 그건 발견이 먼저다.** 낮추지 않고 재봤다:

| | CR 바이트 | md5 |
|---|---|---|
| blob (`origin/main`) | 0 | `6437f1fe…` |
| **작업 트리 (이 Windows 호스트)** | **413** | `387f1e50…` |
| CloudFront (terraform 이 올린 것) | 413 | `387f1e50…` |
| Vercel (리눅스 빌드) | 0 | `2ea624d3…` |

`core.autocrlf=true` 인데 `.gitattributes` 는 `*.sh`/`*.sql`/`*.service`/`*.timer` 만 LF 로 고정한다 —
**`*.html` 은 안 걸려 있다.** terraform 의 `aws_s3_object.index` 는 `source = <작업 트리 파일>` 이라
**체크아웃된 바이트를 그대로 업로드**한다 ⇒

1. **`filemd5` 가 호스트 의존이다.** Linux 에서 apply 하면 etag 가 바뀌어 `index` 가 더러워지고,
   Windows 에서 apply 하면 되돌아간다 — **핑퐁 드리프트**. `TASK-MONO-558` 이 고친 것의 **형제**이고,
   558 덕분에 plan 이 조용해져서 **이제야 보인다**(더러움이 하나뿐이라 그 하나가 눈에 띈다).
2. 같은 커밋에서 **Vercel 과 S3 가 413 바이트 다른 페이지**를 서빙한다.

**고침**: `.gitattributes` 에 `infra/demo/aws/site/*.html text eol=lf` + 재정규화(작업 트리 CR 413→0).
⚠️ **이 PR 이 머지되면 `terraform plan` 이 `index` 를 한 번 더 더럽게 잡는다**(etag 가 LF md5 로 바뀐다).
그건 결함이 아니라 **이 고침이 S3 에 도달하는 경로**다 — apply 한 번이면 두 경로가 영구히 같아진다.

🔵 내 첫 진단 술어(`grep -c $'\r'`)는 **0 을 냈다.** CR 이 413개 있는데도. 바이트로 세고서야 보였다.

## AC-3 — 론처가 낡았다는 사실이 보인다

- `build.sh` 가 `public/build-info.json` 을 낸다(`commit` / `ref` / `index_md5`).
  🔴 **`config.js` 에 넣지 않았다** — 그 파일은 terraform 의 `aws_s3_object.config` 와 **바이트 모양이
  같아야 한다**(`build.sh` 헤더가 명시한 불변식). SHA 를 끼우면 그 불변식이 깨진다.
- `infra/demo/aws/site/check-launcher-fresh.sh` — 판정 = **서빙 바이트 == `origin/main` 바이트**.
  `0`=신선 / `1`=낡음 / **`2`=판정 불가**. 🔴 2 를 0 으로 접지 않는다.

🔴 **대조군 — 같은 값끼리 비교하면 언제나 통과한다.** 그래서 **오리진 두 개**로 확인했다(실측):

```
CloudFront (apply 직후)          → 신선  (rc=0)
Vercel     (rate limit 로 정지)  → 낡음  (rc=1)
```

**같은 판정자 · 같은 시각 · 반대 결론.** `--self-test` 가 이 왕복을 돌리고, 두 결론이 **같으면 실패**한다.

⇒ **이 티켓이 말한 무성음 실패를 숫자로 잡았다**: `TASK-MONO-560` 이 머지된 지 하루가 지나도록
Vercel 론처는 `data-surface` 링크가 **0개**였고(561 판, 18,821 B), URL 은 내내 200 이었다.

# Edge Cases

- **무시 규칙이 과하게 무시한다** — 론처를 고쳤는데 배포가 안 돈다. 증상은 "머지했는데 그대로" 이고
  CI 는 초록이다. AC-1 (1)(2) 가 이 축을 지킨다.
- **두 프로젝트의 Root Directory 가 다르다** — 한쪽에 맞춘 규칙이 다른 쪽에서 경로를 못 맞춘다.
  프로젝트마다 따로 확인한다(하나로 검증하고 둘 다 됐다고 하지 마라).
- **rate limit 이 풀리는 시점** — "24시간" 은 롤링 창일 수 있다. 한 번 통과했다고 해소된 것이 아니다.
- **`main` 이 이미 빨간 상태** — 이 티켓의 고침이 들어와도 창이 안 풀렸으면 여전히 빨갛다.
  그 경우를 "고침 실패" 로 오독하지 마라(AC-0 의 창 계산이 그래서 필요하다).
- **프리뷰 배포와 프로덕션 배포가 한도를 따로 쓰는지** 확인 없이 가정하지 마라.

# Failure Scenarios

- **가장 위험: 빨간 체크만 없애고 끝내는 것.** 체크를 선택으로 내리거나 무시 규칙을 넓게 걸면 색은
  초록이 되지만 **론처는 여전히 낡은 판을 서빙**한다. 그 상태는 이 저장소가 반복해서 당한
  *"아무것도 안 보면서 초록"* 이다. AC-3 이 그래서 있다.
- **한 프로젝트만 보고 둘 다 고쳤다고 하는 것.** `kanggle-fan` 과 `kanggle-portfolio` 는 다른 코드,
  다른 Root Directory, 다른 트리거다.
- **대시보드에서만 고치는 것.** 저장소에 흔적이 없으면 다음 사람은 왜 배포가 안 도는지 알 수 없고,
  이 티켓의 판정도 재현할 수 없다(AC-2).
- **유료 전환으로 넘어가 원인을 안 고치는 것.** 한도가 커져도 *"무관한 커밋이 배포를 굽는다"* 는
  구조는 남고, 언젠가 다시 닿는다. 그리고 AC-3 의 무성음 실패는 플랜과 무관하다.
