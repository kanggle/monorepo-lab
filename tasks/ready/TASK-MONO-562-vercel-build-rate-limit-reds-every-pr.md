# 배경 — 2026-08-20 UTC, `TASK-MONO-554` PR(#3406) CI 에서 관측

PR 의 실질 체크는 전부 초록이었다(`Demo wrapper smoke` 포함 SUCCESS 5 · SKIPPED 39).
그런데 **Vercel 체크 2건이 FAILURE** 였고, 이유를 Vercel 자신이 말했다:

```
Vercel – kanggle-fan        failure   Deployment rate limited — retry in 24 hours.
Vercel – kanggle-portfolio  failure   Deployment rate limited — retry in 24 hours.
target_url: https://vercel.com/khakiman-projects?upgradeToPro=build-rate-limit
```

**내 diff 와 무관하다** — 그 PR 은 `infra/demo/demo.env` · `verify-demo-wrapper.sh` · 태스크 md 2개뿐이고
프런트를 한 줄도 건드리지 않는다.

🔴 **그리고 `main` 이 이미 같은 이유로 빨갛다**(`Vercel – kanggle-fan` failure, 같은 `build-rate-limit` URL).
즉 이것은 한 PR 의 사고가 아니라 **저장소의 지속 상태**다.

## 🔴 왜 지금 생겼나 — 론처가 Vercel 로 옮겨간 뒤의 새 표면

`TASK-MONO-557` 이 론처 정적 페이지를 CloudFront → **Vercel(`kanggle-portfolio`)** 로 옮겼다.
그 전까지 Vercel 프로젝트는 하나였고(`kanggle-fan`), 체크 이름도 `Vercel` 단수였다 —
**#3404·#3405 에서는 `Vercel` / `Vercel Preview Comments` 가 SUCCESS 였다.** 지금은 프로젝트가
둘이라 체크가 둘로 갈렸고, **커밋 하나가 배포 두 개를 굽는다.**

여기에 08-18~08-19 의 티켓 파일링 러시(#3393~#3405, 13 PR)가 겹쳤다. 🔵 **그 PR 들의 대부분은
문서 전용**이었는데도 배포가 돌았다 — 두 프로젝트 어디에도 경로 필터(Ignored Build Step)가 없다.

## 🔴🔴 진짜 위험은 빨간 체크가 아니다 — **론처가 조용히 낡는다**

`infra/demo/aws/site/build.sh` 헤더가 이미 이 구분을 이름 붙여 뒀다(MONO-557 실측):

> 🔵 사이트는 마지막 성공 배포가 계속 서빙해서 **겉으로는 멀쩡했다** —
> **배포가 죽은 것과 사이트가 죽은 것은 다른 사건이다.** URL 만 찔러서는 안 보인다.

rate limit 은 정확히 그 상태를 24시간 만든다. 론처 수정(예: `TASK-MONO-560` 의 방문자 화면 링크,
`TASK-MONO-561` 의 로그인 안내)을 머지해도 **방문자는 옛 페이지를 본다.** 그리고 우리 쪽
증거는 "머지됨 + main 초록(Vercel 빼고)" 이라 **아무도 안 본다.**

⇒ 이 티켓의 무게는 CI 색깔이 아니라 **론처 배포가 무성음으로 실패하는 창** 이다.

# Goal

커밋 하나가 굽는 Vercel 배포 수를 **실제로 필요한 것만** 으로 줄여 rate limit 에 닿지 않게 하고,
닿았을 때 **론처가 낡았다는 사실이 보이게** 한다.

# Scope

## In Scope

- 두 Vercel 프로젝트(`kanggle-portfolio`, `kanggle-fan`)의 **빌드 트리거 조건**.
  저장소 측 수단(`vercel.json` 의 무시 규칙 / `.vercelignore` / Ignored Build Step 커맨드)을 우선한다 —
  대시보드 설정은 저장소에 남지 않아 다음 사람이 알 수 없다.
- 론처 **배포 신선도**를 판정할 수 있게 하는 것(§ AC-3).
- 필요하면 CI 체크 노출 방식(필수/선택) 정리.

## Out of Scope

- **유료 플랜 전환** — 비용 결정이므로 소유자 판단이다. 이 티켓은 그 선택지를 **숫자와 함께 제시**할
  뿐 실행하지 않는다.
- 론처 페이지의 내용 변경 — `TASK-MONO-560`/`561` 소관.
- CloudFront 판으로 되돌리는 것 — `TASK-MONO-557` 이 주소 안정성을 이유로 내린 결정이고, 이 티켓은
  그것을 뒤집을 근거가 없다.

# Acceptance Criteria

**AC-0 — 재측정 (verify-then-act). 🔴 인계된 숫자를 쓰지 마라.**
착수 시점에 **실제로** 센다:

- 두 프로젝트 각각의 **최근 24시간 배포 건수**와 Vercel 이 적용 중인 **실제 한도**
  (플랜 문서의 일반값이 아니라 이 계정에 걸린 값).
- 그 배포들이 **무엇 때문에 트리거됐는지** — 커밋별로. 문서 전용 PR 이 몇 건을 태웠는가.
- 🔴 **판정 축은 "배포 건수" 다.** 저장소 diff 크기·바이트가 아니다. 축을 헷갈리면 "문서 PR 은
  가벼우니 괜찮다" 는 틀린 결론이 나온다 — 가벼워도 **1건은 1건**이다.

**AC-1 — 무관한 커밋이 배포를 굽지 않는다. 🔴 대조군 필수.**

| 칸 | 커밋 내용 | 기대 |
|---|---|---|
| (1) | `infra/demo/aws/site/**` 변경 | `kanggle-portfolio` **빌드함** |
| (2) | `projects/fan-platform/apps/fan-platform-web/**` 변경 | `kanggle-fan` **빌드함** |
| (3) | `tasks/**` 만 변경 | **둘 다 건너뜀** |
| (4) | `libs/**` 등 무관 백엔드 변경 | **둘 다 건너뜀** |

🔴 **(1)(2)를 빼지 마라.** 무시 규칙은 **과하게 무시하는 방향으로 고장 나며**, 그 고장은
"배포가 안 됐다" 가 아니라 **"배포가 조용히 건너뛰어졌다"** 로 나타난다 — AC 의 나머지가
그것을 초록으로 읽는다. 각 프로젝트가 **자기 경로 변경에는 반드시 빌드하는지**를 같은 왕복에서 본다.

**AC-2 — 규칙이 저장소에 있다.**
무시 조건이 대시보드에만 있으면 다음 사람은 그것을 볼 수 없고, 이 티켓의 판정도 재현 불가다.
저장소 파일로 표현하고, 그 파일이 **어느 Vercel 프로젝트의 Root Directory 에 속하는지** 주석으로 적는다.
⚠️ `vercel.json` 은 **스키마가 엄격해 모르는 최상위 키를 거부**한다 — 설명을 `"//key"` 로 끼워 넣지 마라.
`TASK-MONO-557` 이 정확히 그것으로 배포를 깼다(`45bdca743` 성공 → `ea9d5e79c`·`2679b8e41` 연속 실패).
설명의 집은 `build.sh` 다.

**AC-3 — 론처가 낡았다는 사실이 보인다. 🔴 이 AC 가 이 티켓의 핵심이다.**
rate limit 이든 다른 이유든 **배포가 실패한 채 사이트가 옛 판을 서빙하는 상태**를 판정할 수 있어야 한다.
최소한: 배포된 페이지가 **자기가 어느 커밋에서 나왔는지** 말할 수 있어야 한다
(예: `config.js` 나 메타 태그에 빌드 커밋 SHA — `build.sh` 가 이미 `config.js` 를 생성하므로 자리는 있다).

🔴 **판정은 URL 200 이 아니다.** 200 은 낡은 판도 낸다 — 그것이 MONO-557 이 이름 붙인 함정이다.
판정은 **서빙 중인 SHA 가 `origin/main` 의 그것과 같은가** 로 한다.
🔴 **대조군**: 일부러 옛 판을 가리키게 만들었을 때 그 판정이 **다르다고 말하는지** 확인한다
(같은 값끼리 비교하면 언제나 통과한다).

**AC-4 — 선택지를 숫자와 함께 제시한다 (실행하지 않는다).**
AC-0 의 실측을 근거로, 남는 위험과 완화안을 **소유자가 고를 수 있는 형태**로 적는다:
프리뷰 배포 끄기 / 프로젝트 통합 / 유료 전환(월 비용) 등. 각 안의 **잃는 것**을 반드시 같이 적는다 —
특히 프리뷰 배포를 끄면 **머지 전에 론처가 깨진 것을 볼 기회**가 사라진다.

# Edge Cases

- **무시 규칙이 과하게 무시한다** — 론처를 고쳤는데 배포가 안 돈다. 증상은 "머지했는데 그대로" 이고
  CI 는 초록이다. AC-1 (1)(2) 가 이 축을 지킨다.
- **두 프로젝트의 Root Directory 가 다르다** — 한쪽에 맞춘 규칙이 다른 쪽에서 경로를 못 맞춘다.
  프로젝트마다 따로 확인한다(하나로 검증하고 둘 다 됐다고 하지 마라).
- **rate limit 이 풀리는 시점** — "24시간" 은 롤링 창일 수 있다. 한 번 통과했다고 해소된 것이 아니다.
- **`main` 이 이미 빨간 상태** — 이 티켓의 고침이 들어와도 창이 안 풀렸으면 여전히 빨갛다.
  그 경우를 "고침 실패" 로 오독하지 마라(AC-0 의 창 계산이 그래서 필요하다).
- **프리뷰 배포와 프로덕션 배포가 한도를 따로 쓰는지** 확인 없이 가정하지 마라.

# Failure Scenarios

- **가장 위험: 빨간 체크만 없애고 끝내는 것.** 체크를 선택으로 내리거나 무시 규칙을 넓게 걸면 색은
  초록이 되지만 **론처는 여전히 낡은 판을 서빙**한다. 그 상태는 이 저장소가 반복해서 당한
  *"아무것도 안 보면서 초록"* 이다. AC-3 이 그래서 있다.
- **한 프로젝트만 보고 둘 다 고쳤다고 하는 것.** `kanggle-fan` 과 `kanggle-portfolio` 는 다른 코드,
  다른 Root Directory, 다른 트리거다.
- **대시보드에서만 고치는 것.** 저장소에 흔적이 없으면 다음 사람은 왜 배포가 안 도는지 알 수 없고,
  이 티켓의 판정도 재현할 수 없다(AC-2).
- **유료 전환으로 넘어가 원인을 안 고치는 것.** 한도가 커져도 *"무관한 커밋이 배포를 굽는다"* 는
  구조는 남고, 언젠가 다시 닿는다. 그리고 AC-3 의 무성음 실패는 플랜과 무관하다.
