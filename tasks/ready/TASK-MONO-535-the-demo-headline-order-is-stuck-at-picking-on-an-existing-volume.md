# 🔬 실측 (2026-08-15, 로컬 데모 wms 슬라이스 라이브)

`TASK-BE-586`(ADR-MONO-066 B)이 만든 출하 경로가 **이 스택에서 실제로 동작한다**. 다만
갈렸다 — **같은 DB, 같은 코드, 같은 시드 실행**인데:

| 주문 | 생성(UTC) | `picking_request` | 상태 |
|---|---|---|---|
| **`SO-DEMO-0001`** (시드가 만드는 **간판 주문**) | 08-14 12:42 | **0** | **`PICKING`** |
| `SO-BE586-0002` | 08-14 17:38 | 1 | `SHIPPED` |
| `SO-DEMO-0003` | 08-14 17:58 | 1 | `SHIPPED` |

시드는 이것을 **정확히 보고한다**(설계가 옳다):

```
[seed:wms] ⚠ picking request 가 생기지 않았습니다 — ADR-MONO-066 경로를 확인하십시오
[seed:wms] ⚠ 출고 흐름이 SHIPPED 까지 가지 못했습니다 — 주문 화면은 정상이고 출하 화면만 빕니다
[seed:wms] 요약 — 생성 0 · 기존 2 · 실패 0
```

## 왜 재실행으로 안 낫는가

`PickingRequest` 는 **예약 회신 이벤트**(`wms.inventory.reserved.v1`)를 소비할 때 만들어진다
(`InventoryReservedConsumer`, ADR-MONO-066 옵션 B). `SO-DEMO-0001` 의 예약은 그 코드가
존재하기 전에 **이미 소비돼 끝났고**, 컨슈머는 그 이벤트를 다시 읽지 않는다. 시드를 몇 번
돌려도 주문은 이미 존재하므로(멱등) 새 예약이 일어나지 않는다.

🔴 **수동 재진입 경로도 없다.** `TASK-BE-586` 의 R2-b 가 계약 § 2.1
(`POST /orders/{id}/picking-requests`)을 **삭제**했다 — 자기 전제(`saga == REQUESTED`)
때문에 도달 불가였기 때문이고, 그 판단 자체는 옳다. 결과적으로 **이미 `RESERVED` 로 넘어간
주문을 되살릴 API 는 존재하지 않는다.**

⇒ 남는 복구 수단은 **wms 볼륨 초기화 + 재시드**뿐이다.

## 이 저장소는 이 클래스를 이미 한 번 겪었다

워크스루 §6 의 `TASK-BE-581`·`BE-584` 행이 같은 주문에 대해 같은 결론에 도달했다 —
*"🔴 소급 stamp 는 금지라 기존 `SO-DEMO-0001`(`tenant_id=NULL`)은 영원히 안 보였고,
**볼륨 초기화 + 재시드로 닫았다**(2026-08-14)"*. **같은 주문 · 같은 처방 · 다른 원인**으로
두 번째다.

## 진짜 문제는 "요약 줄이 구별하지 못한다" 는 것

`생성 0 · 기존 2 · 실패 0` 은 **완전히 정상인 2회차 실행과 글자 하나 다르지 않다.** 유일한
차이는 그 위 두 줄의 ⚠ 이고, 그 두 줄은 스크롤로 지나간다. 데모를 켜는 사람이 보는 마지막
줄이 *"실패 0"* 이므로 **스택은 초록으로 읽히고 화면만 빈다.**

워크스루 §6 의 `TASK-MONO-510` 행은 시드가 *"피킹 확정 → 포장 → 봉인 → 출하(`SHIPPED`)
까지 실제 API 로 심는다"* 고 **조건 없이** 적고 있다. 그것은 **빈 볼륨에서만** 참이다.

# Goal

기존 볼륨에서 데모를 켠 사람이 **간판 주문이 멈춰 있다는 사실과 그 복구 방법을** 알게 한다.
(주문을 되살리는 도메인 경로를 새로 만드는 것은 이 티켓의 목표가 아니다 — 아래 참조.)

# Scope

**In scope**

- 시드 **요약 줄**이 이 상태를 구별하게 한다. `실패 0` 로 끝나서는 안 된다 — 예: `경고 N`
  을 요약에 포함하거나, 출하까지 못 간 주문 수를 요약 줄에 싣는다.
- 복구 절차(**wms 볼륨 초기화 + 재시드**)를 워크스루 §7 과 시드 경고 문구에 **명령까지**
  적는다. 지금 경고는 *"ADR-MONO-066 경로를 확인하십시오"* 인데, 확인해 봐야 코드는
  정상이므로 **읽는 사람을 잘못된 방향으로 보낸다.**
- 워크스루 §6 의 *"출하까지 심는다"* 서술에 **빈 볼륨 전제**를 단다.

**Out of scope**

- 🔴 **이미 `RESERVED` 인 주문을 되살리는 API 를 새로 만드는 것.** `TASK-BE-586` R2-b 가
  도달 불가라는 이유로 계약에서 지운 표면을 되살리는 것이고, 그것은 **ADR 결정**이다
  (`HARDSTOP-09`). 필요하다는 근거가 생기면 별도 티켓 + ADR 로 간다.
- **이벤트 재생(replay)으로 고치는 것.** 소비된 이벤트를 다시 흘리는 것은 다른 사가에도
  영향을 주는 조작이라 데모 편의로 도입할 성질이 아니다.
- **`SO-DEMO-0001` 을 DB 로 직접 고치는 것.** 시드의 `dbexec --why` 게이트가 막는 그 행위이고,
  소급 stamp 금지 결정(`TASK-BE-581`)과 같은 이유로 하지 않는다.

# Acceptance Criteria

**AC-0 — 재현과 모집단 (verify-then-act).**
착수 시점의 wms 볼륨에서 주문별 `picking_request` 수를 다시 센다
(`select o.order_no, count(p.id) from outbound_order o left join picking_request p on p.order_id = o.id group by o.order_no`).
🔴 **PK 는 `outbound_order.id` 다** — `order_id` 로 조인하면 컬럼이 없어 에러가 나고,
`2>/dev/null` 과 함께 쓰면 **0행을 "그런 주문 없음" 으로 오독**한다(이 티켓을 쓰며 실제로 겪었다).
0건이면 이미 볼륨이 초기화된 것이므로 **그 사실을 적고**, AC-1 의 판정은 인위적 재현으로 만든다.

**AC-1 — 요약 줄이 구별해야 한다 (bite).**
멈춘 주문이 있는 상태에서 시드를 돌려 **마지막 줄만 읽어도** 정상과 다르다는 것을 확인한다.
그리고 **정상 상태(전부 SHIPPED)에서는 그 표시가 나오지 않는 것**도 같은 실행에서 확인한다
— 대조군 없이는 "항상 경고하는 줄" 을 추가한 것과 구별되지 않는다.

**AC-2 — 경고가 올바른 행동을 지시해야 한다.**
현재 문구(*"ADR-MONO-066 경로를 확인하십시오"*)는 **코드가 정상인 경우에 코드를 의심하게
만든다.** 복구 명령(볼륨 초기화 + 재시드)을 문구에 넣고, 그 명령을 **실제로 실행해 주문이
`SHIPPED` 까지 가는 것**을 확인한다(문서에 적은 명령이 동작하는지까지가 AC 다).

**AC-3 — 워크스루 정정.**
§6 `TASK-MONO-510` 행의 *"출하까지 심는다"* 에 **빈 볼륨 전제**를 명시하고, §7 에 이 증상
(주문 화면엔 있는데 출하 화면만 빔)과 복구를 행으로 넣는다.

# Edge Cases

- **볼륨 초기화는 wms 데이터 전체를 지운다** — 입고 흐름·재고·마스터까지. 시드가 전부 다시
  심으므로 복구는 되지만, **그 사실을 복구 안내에 적어야 한다**(모르고 실행하면 놀란다).
- **다른 도메인의 볼륨은 건드리지 않는다** — `demo-down.sh wms -v` 류의 범위를 정확히 적을 것.
- **`SO-DEMO-0001` 만의 문제가 아닐 수 있다** — AC-0 이 주문 전수를 세는 이유다.
- 🔵 **이 상태에서도 격리 대조군은 성립한다**(실측: `/api/wms/shipments` demo-corp **2** vs
  ecommerce **0**, 전역 표면은 1 vs 1). 즉 **ADR-MONO-065 판정은 이 결함의 영향을 받지 않는다** —
  둘을 한 사건으로 묶지 말 것.

# Failure Scenarios

- **요약 줄에 항상 뜨는 경고를 추가하는 것.** 늘 켜져 있는 경고는 읽히지 않는다. AC-1 의
  대조군이 이것을 막는다.
- **"확인하십시오" 를 다른 "확인하십시오" 로 바꾸는 것.** 경고의 값어치는 **다음 행동**을
  주는 데 있다. 명령이 없으면 고친 것이 아니다.
- **볼륨 초기화를 기본 동작으로 만드는 것.** 시드가 데이터를 지우기 시작하면 재실행이
  무서워지고, 그러면 아무도 안 돌린다.
- 🔴 **도메인 결함으로 오진하는 것.** 코드는 정상이다 — `SO-BE586-0002`·`SO-DEMO-0003` 이
  같은 DB 에서 `SHIPPED` 까지 갔다. 데이터 이력의 문제이지 경로의 문제가 아니다.
