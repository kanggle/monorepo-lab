# Goal

`2026-09-08` 에 `terraform apply` 로 묶음 라우트 3개(`GET /bundles` · `POST /bundle/start`
· `POST /bundle/stop`)가 배포됐다. **제어 API 쪽은 완성됐다.** 그런데 그 요청을 실제로
수행하는 쪽 — EC2 인스턴스 — 은 **그 개념을 모른다.**

결과: 방문자가 「팬 플랫폼 · 실시간 기능 시작」을 누르면

1. 람다가 선택 `["fan"]` 을 SSM 에 저장하고 인스턴스를 켠다 — **200 을 낸다**
2. 인스턴스는 `demo-boot.sh full` 을 돌린다 — **SSM 선택을 읽는 코드가 없다**
3. **8도메인 전체가 뜬다.** 팬만 골랐는데 예산은 전체 스택만큼 나간다

🔴 **에러가 아니라 «다른 동작» 이다.** 로그에도 안 보이고, 화면은 정상으로 보인다.
핸들러가 다른 원인(라우트 순서)으로 정확히 이 실패를 경고해 뒀는데, 실제로는 **AMI 세대차**
로 같은 자리에 도착했다.

🔴 어제까지는 안전했다 — 라우트가 없어서 버튼이 **잠겨 있었다.** apply 가 그 잠금을 풀었고,
그래서 이 결함은 **오늘 생겼다.**

# 🔴🔴 재굽기 순서 제약 — 이것부터 읽어라 (2026-09-08 실측)

이 티켓의 근본 해법은 **AMI 재굽기**다. 그런데 **재굽기 전에 반드시 수확해야 하는 측정이
있고, 그것은 재굽기 뒤에 영영 불가능해진다.**

| 실측 | 값 |
|---|---|
| 인스턴스 볼륨 | **루트 하나뿐** — `/dev/sda1` = `vol-078894f6d649d2b5e` |
| 별도 EBS 볼륨 리소스 | **0개** — 도커 볼륨(postgres 데이터 포함)이 루트 위에 있다 |
| `DeleteOnTermination` | **`True`** |
| `TASK-MONO-630` 의 절차 | 재굽기 → `ami_id` 갱신 → `terraform apply` = **EC2 교체** |

⇒ **재굽기 = 인스턴스 교체 = 루트 볼륨 파괴 = 지금 DB 의 마이그레이션 이력 소멸.**

🔴🔴 `TASK-MONO-645` ③ 은 «postgres `V19` 가 **기존 볼륨에** 적용되는가» 다. 교체 뒤에는
V19 가 **빈 DB 의 초기 체인 일부**로 돌아가 순서 결함에 **영구 초록**이 된다.

## 순서

1. 🔴 **재굽기 전에** 지금 인스턴스를 한 번 켜서 `TASK-MONO-645`(와 `TASK-MONO-633`)를
   수확한다. 현재 AMI 로도 **전체 스택 기동은 정상**이다 — 안 되는 것은 묶음 기동뿐이고,
   그것이 바로 이 티켓이다.
2. 그다음 재굽기 → `ami_id` 갱신 → `apply`.
3. 🔵 그래도 이 티켓의 가드는 **여전히 필요하다.** 재굽기는 지금 증상을 지울 뿐이고,
   **세 배포 경로(Vercel 머지 · terraform apply · AMI 재굽기)가 다른 속도로 나가는 것**은
   그대로다. 다음에 `demo-up.sh` 가 바뀌는 날 똑같이 재발한다(§ Failure Scenarios 5).

🔵 즉 **재굽기와 이 티켓은 서로를 대체하지 않는다.** 재굽기는 지금의 거짓말을 없애고,
이 티켓은 다음번을 막는다.

# Acceptance Criteria

## AC-0 — 착수 전 재측정

- [ ] 🔴 **AMI 의 `RepoCommit` 을 다시 읽어라.** 그 사이 소유자가 재굽기를 했다면 재현
      조건이 사라진다 — **그때도 티켓을 닫지 마라.** 판정은 «지금 세대가 맞나» 가 아니라
      **«어긋났을 때 거절하는가»** 다. 맞으면 인위적으로 어긋난 값을 넣어서 재라.
- [ ] 구워진 `demo-boot.sh`·`projects.sh`·`demo-stack.service` 를 다시 열어 위 표를 갱신한다
      (`git show <RepoCommit>:<path>`).
- [ ] 🔴 예산을 다시 재라. 이 결함을 밟으면 **전체 스택 분량**이 나간다.

## AC-1 — 세대가 어긋나면 묶음 기동을 거절한다

- [ ] 🔴 **판단은 «AMI 의 `RepoCommit` 이 묶음 기동을 아는가» 로 한다.** 하드코딩 스위치로
      끄지 마라 — 그러면 재굽기 뒤에 **이 코드를 또 고쳐야 하고**, 그 티켓이 안 만들어지면
      기능이 영원히 꺼진 채로 남는다. 세대를 읽으면 재굽기 순간 **저절로 풀린다.**
- [ ] 🔴 «안다» 의 판정을 **무엇으로 할지 정하고 근거를 적어라.** 후보: ① AMI 태그
      `RepoCommit` 이 `9f0fcd2d6` 의 자손인가 ② 인스턴스에서 파일을 직접 grep. ①은 인스턴스가
      꺼져 있어도 되지만 조상 판정이 필요하고, ②는 정확하지만 **running 이어야** 한다 —
      즉 «켜기 전에 막는다» 는 목적에 ②는 못 쓴다. 이 제약을 적고 고르라.
- [ ] 거절은 **`bundle_start` 에서** 한다 — 행위가 일어나는 자리다. `/bundles` 에서만
      막으면 API 를 직접 부르는 경로가 남는다.
- [ ] 🔴 **`/start`(전체 스택)는 막지 않는다.** 그건 구워진 AMI 가 아는 동작이고 지금도
      정상이다. 둘을 같이 막으면 데모가 통째로 멈춘다.

## AC-2 — 화면이 왜 못 하는지 말한다

- [ ] `/bundles` 응답이 이 상태를 **말하고**, 론처가 버튼을 잠그며 **사유를 표시**한다.
- [ ] 🔴 문구는 «준비 중» 같은 모호한 말이 아니라 **무엇이 필요한지**를 말한다 —
      「데모 서버 이미지가 이 기능보다 오래됐습니다(관리자 재배포 필요)」 수준.
- [ ] 🔴 `TASK-MONO-636` 이 정한 상태 표에 **행을 더한다**(기존 행을 바꾸지 마라).
- [ ] 🔵 `TASK-MONO-644` 와 **다른 결함**이다. 644 는 「404 가 CORS 없이 와서 분기에 도달
      못 함」이고 이건 「분기는 도달하는데 저쪽이 그 기능을 모름」이다. 섞지 마라.

# Edge Cases

| 상황 | 기대 |
|---|---|
| AMI 가 최신 | 묶음 기동이 **정상 동작**. 거절 없음 |

# Failure Scenarios

1. **하드코딩으로 묶음 기동을 꺼 둔다** → 재굽기 뒤에도 꺼진 채로 남고, 그걸 켜는 티켓이
   안 만들어지면 `ADR-MONO-071` 이 영원히 죽는다.
2. **`/start` 까지 같이 막는다** → 지금 되는 유일한 기동 경로를 없앤다.
3. **`/bundles` 에서만 막는다** → API 를 직접 부르는 경로가 남는다. 가드는 **행위가
   일어나는 자리**에 있어야 한다.
4. **644 와 합친다** → 원인이 다르고 처방이 다르다. 하나를 고쳐도 다른 하나가 남는다.
5. **재굽기를 해서 증상만 지우고 닫는다** → 세 배포 경로는 계속 다른 속도로 나간다.
   다음에 `demo-up.sh` 가 바뀌는 날 똑같이 재발한다.
6. **가드가 AWS 를 부른다** → CI 에 자격증명이 없어 영구 빨강이거나 영구 skip 이 된다.
