# Acceptance Criteria

## 🔴 AC-0 — verify-then-act 게이트 (달력 확인이 아니다)

착수 전에 **아래를 실제로 재고**, 하나라도 어긋나면 **STOP** 하고 이 티켓을 고친다.

```bash
# (a) 소유자 승인이 있는가 — 재굽기와 기동 각각
# (b) 현재 AMI 가 여전히 대상들보다 앞서는가
aws ec2 describe-images --owners self \
  --query 'reverse(sort_by(Images,&CreationDate))[:1].{id:ImageId,created:CreationDate}' --output text
# (c) 예산이 남아 있는가 (기동 1회 ≈ 11분 + 확인 시간)
curl -s "$DEMO_API_BASE/status" | tee /dev/stderr   # used_minutes / budget_minutes
```

🔴 **(b)가 이미 최신이면** ①②는 이미 이미지에 들어 있다는 뜻이므로 **재굽기 없이 기동만** 하면 된다.
그 경우 이 티켓의 비용이 크게 줄어든다 — **재지 않고 재굽기부터 하지 마라.**

## AC-1 — 재굽기는 **한 번**, ref 를 기록한다

`packer build -var "repo_ref=main"`. 🔴 **어느 커밋이 구워졌는지 적어라** — 그것이 ①②④⑤의
판정 근거이고, 안 적으면 *"왜 아직 옛 화면이 보이지"* 를 다시 발굴하게 된다.

## AC-2 — 기동은 **한 번**, 다섯 항목을 그 창 안에서 전부 확인한다

🔴 **항목마다 따로 기동하지 마라.** 예산이 그것을 허용하지 않고(잔여 104분), 그렇게 하면
이 티켓의 존재 이유가 사라진다.

각 항목의 판정 방법은 **원 티켓의 AC 를 따른다** — 여기서 다시 쓰지 않는다(같은 사실을 두 곳에
적으면 한쪽만 고쳐진다). 각 원 티켓의 AC-4 를 열어서 그대로 수행한다.

## AC-3 — 결과를 **원 티켓에** 기록하고 닫는다

- `TASK-BE-580` · `TASK-BE-581` → `review/` → `done/` (각 프로젝트 lifecycle)
- ④ 결과 → `TASK-MONO-580` 종결 근거에
- ⑤ → 컨테이너 제거가 실제로 반영됐는지 **호스트에서** 확인

🔴 **어긋나는 항목이 하나라도 있으면 그것만 남기고 나머지는 닫는다.** 하나 때문에 전부 미루면
다음 재굽기까지 또 밀린다.

## AC-4 — ⑤(컨테이너 제거)의 순서

🔴 **`TASK-MONO-580` 이 머지된 뒤에** 제거한다. 순서가 뒤집히면 방문자가 **어느 쪽에서도** 스토어를
못 본다(Vercel 판은 아직 없고 데모 사본은 지워진 상태).

제거 후 `web.ecommerce.<DEMO_DOMAIN>` 은 **404 가 되는 것이 정상**이다 — 그것이 전환 완료의 신호다.

## AC-5 — 🔵 이 티켓은 **닫히면 사라진다**

다섯이 다 끝나면 종결한다. 나중에 또 밀리면 **새 번들 티켓**을 만든다 — 이 티켓을 영구
대기실로 재사용하지 마라(영구 대기실은 아무도 안 읽는다).
