# Task ID

TASK-FAN-FE-017

# Title

아티스트 상세의 팔로우 버튼이 **자기 상태를 모른다** — `initialFollowing` 이 하드코딩 `false` 라, 이미 팔로우한 아티스트도 "팔로우" 로 보이고 언팔로우까지 두 번 눌러야 한다

# Status

review

# Owner

fan-platform

# Task Tags

- frontend
- community

# 배경

2026-08-16 팬 웹 브라우저 실측(워크스루 §3 화면 전수 확인) 중 발견했다.

`app/(main)/artists/[id]/page.tsx` 는 팔로우 버튼을 이렇게 렌더한다:

```tsx
<FollowButton
  artistAccountId={artist.accountId}
  artistId={artist.id}
  initialFollowing={false}      // ← 상수
/>
```

`FollowButton` 은 `useState(initialFollowing)` 하나로만 라벨을 정하므로
(`following ? '팔로잉' : '팔로우'`), **서버가 아는 실제 팔로우 관계가 화면에 한 번도
도달하지 않는다.** 아티스트 상세 페이지는 서버 컴포넌트라 세션 토큰을 들고 있고 프로필을
이미 한 번 가져오는데, **팔로우 여부만 안 물어본다.**

# 실측 (2026-08-16, Chromium · 대조군으로 판정)

🔴 **처음 세운 가설은 틀렸다.** 소스만 읽고 *"이미 팔로우 중이면 누르면 409 가 나고
`catch` 가 삼켜서 아무 일도 안 일어난다"* 로 적었는데, **눌러 보니 아니었다.**

대조군은 *"눌러도 아무 일 없다"* 와 *"이미 팔로우라 그런 것"* 을 가르기 위해 **두 아티스트**로
잡았다 — 시드가 팔로우한 **노아**(관계 있음) vs 팔로우하지 않은 **세아**(관계 없음).

| 대상 | 누르기 전 라벨 | `aria-pressed` | 클릭 결과 | 누른 뒤 라벨 |
|---|---|---|---|---|
| **노아** (이미 팔로우 중) | `팔로우` | `false` | 서버 액션 **성공** | `팔로잉` |
| **세아** (팔로우 안 함) | `팔로우` | `false` | 서버 액션 **성공** | `팔로잉` |

> 🔴 **정정 (2026-08-16, 위 표의 초판을 고친다).** 초판은 이 칸을 **"POST 200"** 이라고
> 적었다. 그 200 은 **Next 서버 액션의 전송 상태**이지 community API 의 상태가 아니다 —
> 브라우저가 본 `POST` 는 페이지 URL(`/artists/<id>`) 로 가는 액션 호출이다. 실제로
> community 는 노아에 대해 **409 `ALREADY_FOLLOWING`** 을 냈고, `features/follow/api/actions.ts`
> 가 그것을 **의도적으로 삼킨다**(`if (err.code === 'ALREADY_FOLLOWING') return;` — 주석이
> *"Idempotent at the UI level"* 로 그 의도를 밝히고 있다). 같은 실행에서 시드도 재팔로우에
> **HTTP 409** 를 받았다(`존재  팔로우(루미) (HTTP 409)`) — **같은 사건의 두 관측이 서로
> 다른 숫자로 보인 것**이고, 갈린 이유는 두 관측이 **다른 층**을 봤기 때문이다.
>
> 🔵 **그래서 첫 가설도 절반은 맞았다** — *"409 를 catch 가 삼킨다"* 는 참이다. 틀린 것은
> **어느 파일이냐**였다: `FollowButton` 의 빈 `catch` 가 아니라 `actions.ts` 의 **명시적
> 삼킴**이고, 후자는 `throw` 하지 않고 정상 반환하므로 `setFollowing(true)` 에 **도달한다**.
> 그것이 라벨이 바뀐 이유다. 층을 틀리면 같은 메커니즘이 **정반대 결론**을 낸다.

⇒ **버튼은 작동한다.** 결함은 더 좁고 정확하다:
**초기 상태가 서버에서 오지 않는다.** 두 칸이 **구별되지 않는다**는 것 — 관계가 있는 쪽과
없는 쪽이 똑같이 `팔로우 / aria-pressed=false` 로 렌더되는 것 — 이 결함의 지문이다.

🔵 세아는 실측 직후 다시 눌러 **원상복구**했다(라벨 `팔로우` 확인). 노아는 이미 팔로우
상태였으므로 재팔로우가 상태를 바꾸지 않았다.

## 사용자에게 보이는 피해

1. **화면이 관계를 말하지 않는다** — 아티스트 상세는 "내가 이 아티스트를 팔로우하는가" 를
   답할 수 있는 유일한 화면인데, 언제나 "아니오" 처럼 보인다.
2. **언팔로우 경로가 사실상 없다** — 언팔로우하려면 먼저 `팔로우` 를 눌러 `팔로잉` 으로
   만든 뒤 다시 눌러야 한다. 즉 **의도치 않은 재팔로우를 반드시 거쳐야** 언팔로우에 닿는다.
3. 🔴 **피드가 이 거짓을 가린다** — 홈 피드는 팔로우한 아티스트의 글만 보여주므로 실제 관계는
   **정상**이다. 화면 하나만 틀렸고 다른 화면은 맞으므로, "팔로우가 안 됐나 보다" 로
   오진하기 쉽다.

# Scope

- 팔로우 여부를 조회하는 경로를 확정한다. 🔴 **먼저 계약을 읽어라** — 이 티켓은 "없으면
  만들라" 고 말하지 않는다. 세 갈래이고 어느 쪽인지는 `specs/contracts/` 가 답한다:
  1. community 계약에 단건 조회(`GET …/follows/{artistAccountId}` 류)가 **있다** → 그대로 쓴다.
  2. 내 팔로우 **목록** 조회만 있다 → 상세에서 그것을 부르고 대상 포함 여부로 판정한다.
  3. 둘 다 없다 → **HARDSTOP-08**(필요 계약 부재). 계약을 먼저 갱신하고 그 다음 구현이다.

> ⛔ **이 갈림길은 이미 밟았다 — 3번이다 (2026-08-16 게이트 수행, HARDSTOP-08 발동).**
>
> | 축 | 결과 |
> |---|---|
> | `community-api.md` § Follows | `POST /api/community/follows` · `DELETE …/{artistAccountId}` — **끝** |
> | community 의 다른 `GET` | `posts/{id}` · `posts/mine` · `feed` — 팔로우 상태를 답하는 것 없음 |
> | `artist-api.md` 의 `GET /api/artists/{id}` | 팔로우 플래그 **없음** |
> | `FollowController` (코드) | `@PostMapping` + `@DeleteMapping` — **`@GetMapping` 없음** |
>
> **계약과 코드가 일치한다** ⇒ 드리프트가 아니라 **진짜 공백**이다. 🔴 `feed` 로 때우는
> 우회는 **금지**다: 그것은 팔로우한 아티스트의 *글* 을 주므로 **"팔로우 중 · 글 없음"**
> 과 **"팔로우 안 함"** 이 구별되지 않는데, 이 화면은 정확히 *아직 글이 없는 아티스트를
> 발견해 팔로우하는* 경로에 놓여 있다 — 틀리는 경우가 예외가 아니라 **주 용도**다.
>
> ⇒ **선행 티켓 `TASK-FAN-BE-049` 를 세웠다**(계약 + community-service 읽기 경로).
> **이 티켓은 그것이 머지된 뒤에 착수한다.** 지금 착수하면 계약 없는 엔드포인트를
> 추측으로 부르거나, 위의 금지된 우회를 하게 된다.
- `artists/[id]/page.tsx` 가 프로필 fetch 와 나란히 그 값을 읽어 `initialFollowing` 으로 전달.
- `FollowButton` 자체는 이미 `initialFollowing` 을 받도록 설계돼 있다 — **컴포넌트는 고칠
  것이 없을 가능성이 높다.** 필요 이상으로 건드리지 않는다.

## Out of Scope

- 팔로우/언팔로우 **동작** 자체 — 실측으로 정상 확인됐다(양쪽 POST 200).
- `FollowButton` 의 빈 `catch` — 실패를 사용자에게 알리지 않는 것은 별개의 사실이고, 이번
  실측에서는 **발화하지 않았다**(오류 0건). 추측으로 묶지 않는다.
- 디렉터리(`/artists`) 카드에 팔로우 상태를 표시하는 것 — 새 기능이지 이 결함의 수정이 아니다.

- [x] **AC-4** — 유닛 테스트가 `initialFollowing=true` 를 받은 버튼이 `팔로잉` 을 렌더하고

      페이지가 상수를 넘기던 회귀가 이 테스트에 **잡히도록**, 페이지 레벨에서 값이 전달되는
      것까지 확인한다(컴포넌트만 테스트하면 원래 결함은 초록으로 통과한다 — 원래 결함은

      반복 재발한 게이트다).

# Edge Cases

- **자기 자신** — 팬이 아티스트인 계정(시드의 루미·노아)이 자기 상세를 열었을 때 버튼이
  무엇이어야 하는지는 정해진 바 없다. 이번 실측에서는 팬 계정으로만 봤다. 계약이 답하지
  않으면 **현 동작을 유지**하고 별건으로 남긴다 — 이 티켓에서 새 규칙을 만들지 않는다.
- **`accountId` vs `id`** — 팔로우 API 가 검증하는 것은 `artist.accountId` 이고 `artist.id` 가
  아니다(`TASK-FAN-BE-045` 가 그 주석을 코드에 남겼다). 조회도 **같은 축**을 써야 한다.
  🔴 데모 행에서는 두 값이 우연히 일치하므로 **틀린 축을 써도 데모는 초록이다.**
- **비로그인** — 미들웨어가 상세를 보호하므로 이 경로는 로그인 상태만 도달한다. 다만 세션은
  있는데 토큰이 없는 상태(`getFanSession` 이 `accessToken: null` 을 내는 경우)가 실재한다 —
  그때 조회가 실패하면 `false` 로 **폴백**하되, 그것이 "팔로우 안 함" 으로 **보이는** 것이
  현재 결함과 같은 모양임을 기억할 것.

# Failure Scenarios

- **한 아티스트로만 검증한다** → 팔로우 안 한 아티스트를 골랐다면 지금 상태로도 통과한다.
  AC-2 의 두 칸이 이 실패를 막는다.
- **`artist.id` 로 팔로우 여부를 조회한다** → 데모 데이터에서는 두 값이 같아 **초록**이고,
  실제 IAM 신원으로 등록된 아티스트에서만 틀린다 — 데모가 절대 못 잡는 결함이다.
- **컴포넌트 기본값만 바꾼다**(`initialFollowing = true`) → 방향만 뒤집혀, 팔로우하지 않은
  아티스트가 `팔로잉` 으로 보인다. 결함의 자리는 기본값이 아니라 **호출부가 실제 값을 안
  넘긴다**는 것이다.
- **상세에서 목록 전체를 매번 가져온다**(Scope 2 경로) → 팔로우가 많아지면 상세 렌더가
  느려진다. 계약에 단건 조회가 있으면 그쪽이 먼저다.

# ✅ 실행 결과 (2026-08-17)

## 갈림길은 이미 답이 나 있었다

`TASK-FAN-BE-049` 가 Scope 3번(계약 부재)을 닫으면서 읽기 경로를 열었으므로, 이 티켓은

**호출부**가 리터럴 `false` 를 넘긴 것이다. Scope 가 *"컴포넌트는 고칠 것이 없을
가능성이 높다"* 로 예측했고 그대로였다 — 변경은 값 하나와 그 값을 얻는 호출뿐이다.


**정확히 구별하는 칸 하나만 빨개졌다.** 나머지 셋(컴포넌트 축 · 축 검사 · "팔로우" 케이스)은
상수로도 통과하는 칸들이고, 그 점은 테스트 주석이 미리 적어 둔 그대로다 ⇒ 이 스위트는
**AC-2 의 한 칸에만 이빨이 있고**, 그 칸이 없으면 전부 초록이다.

## 🔴 첫 테스트가 아무것도 재지 않았다 — Suspense fallback 만 렌더했다

처음에는 **라우트**(`app/(main)/artists/[id]/page.tsx`)를 렌더했는데, 라우트가
`<Suspense>` 로 감싸고 있어 RTL 이 **fallback("아티스트 프로필을 불러오는 중...")만**
그렸다. 결과는 `getFollowStatus` **호출 0회** — 즉 초록이었다면 *아무것도 재지 않은 초록*
이었을 것이다.

고침 = 프로필 본문을 `features/artist/ui/ArtistProfile.tsx` 로 옮기고 테스트가 그것을
**직접 await** 한다. 🔵 이 이동은 이 저장소의 기존 관례와 같은 방향이다 — 프런트 테스트는
전부 `features/*/ui` 컴포넌트와 api 모듈을 대상으로 하고, **라우트를 렌더하는 테스트는
하나도 없었다**(그럴 만한 이유가 있었던 것이다). 라우트 파일은 이제 Suspense 경계와
파라미터 해소만 남는다.

## 🔵 폴백을 남긴 자리와 그 대가

`getFollowStatus` 는 실패 시 `false` 를 돌려준다. 프로필이 에러 화면이 되는 것보다는
낫지만, **일시 실패가 "팔로우 안 함" 처럼 보이는 것은 이 티켓이 고친 결함과 같은 모양**
이다. 그래서 폴백은 *호출 대신*이 아니라 *호출 뒤*에 둔다 — 순간의 blip 에는 허용,
정상 상태로는 불가. 이 구분을 코드 주석에 적었다.

## 범위 밖으로 두고 온 것

- 디렉터리(`/artists`) 카드의 팔로우 상태 표시 — 새 기능이다. `BE-049` 계약이 목록형
  조회를 **덧붙일 수 있게** 열어 뒀다(단건과 충돌하지 않는다).
- `FollowButton` 의 빈 `catch` — 이번에도 발화하지 않았다. 추측으로 묶지 않는다.
- 자기 자신(아티스트가 자기 상세를 여는 경우) — 계약이 답하지 않아 현 동작 유지.
