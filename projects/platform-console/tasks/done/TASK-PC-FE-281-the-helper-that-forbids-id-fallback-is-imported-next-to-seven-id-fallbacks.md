# Goal

`{code ?? id}` 로 **raw UUID 로 되돌아가는 마스터 참조 칸 7곳**을 `masterRefLabel` 로 바꾼다.
🔵 그 헬퍼는 **이미 이 앱에 있고**(`shared/lib/master-ref-label.ts`, `TASK-PC-FE-276`),
자기 문서에 하지 말라고 적어 둔 것이 정확히 이 폴백이다:

> 🔴🔴 마지막 줄이 이 함수의 요점이다. **id 폴백은 결함을 «가끔» 되살리고, 그때는 아무도
> 안 본다** — 화면은 대부분의 행에서 이름을 보여주므로 한두 행의 UUID 는 눈에 안 띈다.

# 🔴 왜 지금인가 — **`TASK-MONO-659` 가 한 칸만 고쳐서 화면이 어긋났다**

659 는 생산자(admin-service)에 `warehouseCode` 를 실어 「창고」 칸을 `masterRefLabel` 로
바꿨다. 🔴 그런데 **같은 패널의 형제 칸들은 그대로 `{code ?? id}`** 다. 결과:

| `WmsInventoryDetailPanel` 의 한 화면 | 코드가 null 일 때 보이는 것 |
|---|---|
| 창고 (659 가 고침) | `이름 확인 불가` |
| 위치 · SKU · 로트 (그대로) | 🔴 **raw UUID** |

⇒ **같은 화면이 같은 상황에 두 가지 말을 한다.** 🔵 659 를 탓할 일이 아니다 — 그 티켓의
§ 제외가 *"콘솔 화면 수정 — 277 이 했다"* 로 선을 그었고, 이것은 «생산자가 값을 안 보낸다»
가 아니라 **«콘솔이 받은 null 을 잘못 표현한다»** 라서 부류가 다르다.

## 🔵 그리고 이 결함은 라이브에서 관측됐다

`TASK-MONO-645` ④ 가 데모 창에서 `/wms/inventory` 상세가 **세 칸을 raw UUID 로** 그리는
것을 봤다(위치 · SKU · 창고). 🔴 그때는 «생산자가 코드를 안 싣는다» 로 읽혔는데,
659 구현 중에 **선언은 처음부터 있었다**는 것이 드러났다 — 값이 null 일 때 id 로
되돌아간 것이다. ⇒ **관측은 맞았고 귀속이 틀렸다.**

## 제외 — 🔴🔴 **그 행 «자신의» 식별자 3곳은 다른 부류다. 바꾸지 마라**

| 파일 | 칸 | 왜 제외인가 |
|---|---|---|
| `WmsAsnDataTable.tsx:78` | `asnNo ?? asnId` | |
| `OutboundDrillSummary.tsx:24` | `orderNo ?? orderId` | |
| `OutboundOrdersDataTable.tsx:69` | `orderNo ?? orderId` | |

🔴 이 셋은 **다른 엔티티를 가리키는 참조가 아니라 그 행 자신의 업무 번호**다. 해석할
«이름» 이 애초에 없으므로 `masterRefLabel` 의 세 상태(`—` / `CODE · 이름` / `이름 확인 불가`)가
성립하지 않는다. 🔴🔴 그리고 `이름 확인 불가` 로 바꾸면 **그 행을 식별할 방법이 화면에서
사라진다** — 운영자는 그 행을 지목할 무언가가 있어야 한다. ⇒ **UUID 폴백이 여기서는 옳다.**

🔵 `master-ref-label.ts` 자신이 *"마스터 참조 컬럼의 표시 문자열"* 이라고 범위를 적어 뒀다.
이 구분을 안 하면 «헬퍼를 일관되게 쓴다» 가 **화면을 더 나쁘게** 만든다.

## 제외 — 생산자 변경

없다. 🔵 일곱 칸 전부 **코드가 이미 응답에 온다**(zod 선언 실재). 이 티켓은 **표현만** 바꾼다.
