# audit-memory

메모리 전체를 감사하여 문제를 발견·분류하고, 확인 후 수정한다.

## Usage

```
/audit-memory          # 전체 감사 후 보고서 출력 → 확인 → 수정
/audit-memory --dry-run  # 보고서만 출력, 수정하지 않음
```

## Procedure

### Phase 1: 메모리 수집

1. `MEMORY.md` 인덱스를 읽는다.
2. 인덱스에 나열된 모든 메모리 파일을 읽는다.
3. `CLAUDE.md` 전문을 읽는다 (Phase 4·5 비교용).

### Phase 2: 검사 실행

아래 5가지 기준을 **병렬**로 검사한다. 발견된 모든 문제를 수집하되 이 단계에서는 수정하지 않는다.

#### 2-1. Stale (낡은 내용)

- 완료된 작업이 "진행 중" 또는 미래 시제로 남아 있는가?
- 날짜·버전·브랜치명이 현재 git 상태(`git log`, `git branch`)와 일치하는가?
- 해결된 blocker/이슈가 여전히 미해결로 기술되어 있는가?
- 메모리에 언급된 파일·디렉터리가 현재 저장소에 실제로 존재하는가?

> 검증 방법: `git log --oneline -20`, 해당 파일 경로 존재 여부 확인.

#### 2-2. 모순/불일치 (Contradiction)

- 두 메모리 파일이 같은 사실을 서로 다르게 기술하는가?
- `MEMORY.md` 인덱스의 한 줄 요약이 실제 파일 내용과 다른가?
- 날짜·버전·결정 사항 등 사실 정보가 파일 간에 어긋나는가?

#### 2-3. 댕글링 참조 (Dangling Reference)

- `MEMORY.md` 인덱스의 `[Title](file.md)` 링크가 존재하지 않는 파일을 가리키는가?
- 메모리 파일 본문에서 언급한 spec/task/파일 경로가 저장소에 없는가?

> 검증 방법: `Glob` 또는 `Read` 로 각 경로 실재 여부 확인.

#### 2-4. CLAUDE.md 중복 (Duplicate)

- 메모리에 기록된 규칙·정책이 `CLAUDE.md`(또는 `platform/`, `rules/` 등 상위 소스)에 이미 동일하게 명시되어 있는가?
- 중복된 메모리는 삭제 대상이다. 단, 메모리가 CLAUDE.md보다 더 구체적인 예시나 맥락을 추가하는 경우는 중복으로 보지 않는다.

#### 2-5. 공통 규칙 후보 (Promote-to-CLAUDE.md)

- 개인 선호가 아닌 **레포 전체**에 적용할 규칙인데 메모리에만 존재하는가?
- 판단 기준: "이 규칙이 다른 개발자나 다른 AI 세션에도 동일하게 적용되어야 하는가?"
  - Yes → CLAUDE.md 또는 해당 `platform/`/`rules/` 파일 승격 후보
  - No (개인 작업 스타일, 특정 프로젝트 일회성 결정) → 메모리에 유지

#### 2-6. 인덱스 예산 (TASK-MONO-529)

인덱스는 **매 세션 자동 로드**되므로 크기가 곧 토큰 비용이다. 그런데 이 한도를 검사하는
것은 이 단계뿐이다 — 훅(`.claude/hooks/`)은 분류기 차단이고, `MEMORY.md` 는 리포 밖
(`~/.claude/projects/<slug>/memory/`)이라 CI 가 원리적으로 못 본다.

**① 게이트는 하나가 아니다. 축마다 재는 것이 다르고, 한도는 그 축의 것이다.**

🔴🔴 **여기서 «지표는 하나» 라고 쓰면 그것이 네 번째 재발이다.** 이 절은 세 번 정정됐고
세 번 모두 **축을 하나로 정한 뒤 숫자만** 갈아 끼웠다. 그리고 2026-08-27 에 **셋째 축이
나왔다** — 즉 이 목록도 상한이 아니다. 정경 = 에이전트 메모리
`feedback_memory_index_one_line_discipline`.

| # | 게이트 | **재는 것** | 임계 | 판정자 | 판정용? |
|---|---|---|---|---|---|
| ① | 하네스 메모리 훅 | **문자 수** | 24.4KB ≈ **24,986자** (압축 목표 17.1KB ≈ 17,510자) | 하네스 | **판정** |
| ② | `memory-budget-check.ps1` | **줄 수** | **140줄 미만** (`$LineLimit` — 🔵 하네스 요구치의 **인용**, 자체 유도 아님) | 리포 훅 | **판정** |
| ③ | 하네스 PostToolUse | **줄 수** | 200줄 읽기 한도 · **140줄 미만**을 요구 | 하네스 | **판정** |

- **①·③ 의 출처는 발화 문구뿐이다** — 훅 소스에 접근할 수 없다. 인용할 때 **관측 일자를
  같이 적어라**. ① 은 2026-08-23 관측(*"MEMORY.md is 20.9KB, approaching the 24.4KB read
  limit. Compact it to under 17.1KB"* — 그때 21,388자 ÷ 1024 = 20.9KB 로 문자 축과 일치),
  ③ 은 2026-08-27 관측.
- 🔴 **`24,576` 은 위 어느 임계도 아니다.** 그 값은 ② 의 `$HardLimitBytes` 이고, 훅 주석이
  스스로 *"참고용(보고에만 사용, 판정은 포인터로 한다)"* 이라고 적어 둔 **바이트** 상수다.
  ② 의 판정에도 안 쓰인다.
- 🔴 **바이트는 어느 게이트의 판정에도 안 쓰인다.** 이 파일들은 한글이 많아 UTF-8 로는
  바이트 ≈ 1.4 × 문자이므로, **`wc -c` 로 재면 한도 아래인 파일이 초과처럼 보인다.**
  (2026-08-28 실측: `MEMORY.md` 20,078자 = 28,180B.)
- 🔴 **`/audit-memory` 는 ③ 을 보지 못한다** — 이 커맨드가 재는 것은 ①②뿐이다. 그래서
  ③ 이 발화 중일 때 이 감사는 **PASS 를 보고할 수 있다.** 2026-08-28 이 정확히 그 상태였다
  (① WITHIN · ② **168줄/140 → 발화** · ③ 168줄 → 발화). 감사 결과가 «PASS» 라고 해서
  하네스 경고가 꺼지지는 않는다.

```bash
cd <memory-dir>
node -e "
for (const f of ['MEMORY.md','PLAYBOOKS.md','ARCHIVE.md']) {
  const s = require('fs').readFileSync(f, 'utf8');
  const hook = (s.match(/\]\([a-z0-9_]+\.md\)/g) || []);        // 훅과 '같은' 정규식 = ②의 판정값
  const all  = (s.match(/\]\([a-zA-Z0-9_.-]+\.md\)/g) || []);   // 넓은 정규식 = 실제 총 포인터
  const path = all.reduce((a, b) => a + b.length, 0);
  console.log(f, s.length + '자', Buffer.byteLength(s,'utf8') + 'B',
              s.split('\n').length + '줄',
              '훅ptr' + hook.length, '총ptr' + all.length + '(고유' + new Set(all).size + ')',
              '경로' + path + '자(' + Math.round(path / s.length * 100) + '%)');
}"
```

🔴🔴 **두 정규식은 다른 것을 세고, 어느 쪽도 «틀린» 것이 아니다 — 질문이 다르다.**
훅(`memory-budget-check.ps1:62`)은 `[a-z0-9_]+` 를 쓴다. 그러니 **«훅이 울까» 를 물으려면
훅과 같은 정규식**이어야 한다. 넓은 `[a-zA-Z0-9_.-]` 는 `](ARCHIVE.md)` · `](PLAYBOOKS.md)` ·
하이픈 든 `*_detail_*` 까지 잡아 **총 포인터**를 세지만, 그 값으로 ② 를 예측하면 어긋난다 —
2026-08-28 실측 **훅 179 vs 총 184**. 둘 다 이름을 달고 출력해야 하는 이유가 이것이다.

🔴🔴 **옛 공식 `정원 = 24576 ÷ (포인터당 바이트)` 는 철회됐다 — 단위가 섞여 있었다.**
분자는 문자 한도이고 분모는 바이트였다. 이 나눗셈이 낸 "상한 176 포인터" 때문에
**여유 4,215자가 남은 파일을 초과로 판정**한 적이 있다(2026-08-21). 정경 = 에이전트
메모리 `feedback_memory_index_one_line_discipline` § 2026-08-22.

**② 축을 섞지 마라 — 그리고 처방은 축마다 다르다.**

| 축 | 재는 것 | 누가 본다 | **무엇을 줄여야 내려가나** |
|---|---|---|---|
| **문자 수** (①) | 매 세션 컨텍스트 토큰 비용 | 하네스 · 이 단계의 WITHIN/OVER 판정 | 산문 압축이 **일부** 듣는다 |
| **포인터 개수** (②) | 항목 수 | 리포 훅의 발화 임계 | **항목 수만** — 산문을 깎아도 안 내려간다 |
| **줄 수** (③) | 읽기 한도 | 하네스 · **이 커맨드는 못 본다** | **항목 수** (포인터 1개 ≈ 줄 1개) |

⇒ **축들이 서로 어긋나는 것은 정상이다.** 2026-08-28 실측: ① WITHIN(20,078/24,986) ·
② **발화(168줄/140)** · ③ 발화(168줄). 셋이 같은 방향을 가리킬 이유가 없다.

🔴 **그러니 훅이 울 때 압축부터 하지 마라 — 산문을 아무리 깎아도 ②③ 은 안 꺼진다.**
②③ 을 끄는 유일한 방법은 **항목 수**를 줄이는 것(완료분→ARCHIVE · 절차→PLAYBOOKS ·
항목 통합)이고, 그건 아래 ③ 3번과 같은 **소유자 결정**이다. 🔴 산문만 깎으면 ① 만 조금
내려가고 ②③ 은 그대로다 — 이것이 "압축했는데 왜 아직 우나" 의 답이다.

**②-2 압축 여지는 재고로 판정한다 — "해봤는데 안 되더라" 를 상수로 믿지 마라.**

압축 가능한 표면 = `문자 − 포인터 경로`. **포인터 경로는 주소라 압축 불가**이고, 항목이
늘수록 이 바닥이 올라간다. 2026-08-23 실측: 경로가 **9,756자 = 전체의 46%** — 즉 두 번
깎고 나면 파일의 절반이 파일명이라 **압축으로는 더 못 간다.**

🔴 이 절에는 *"줄 병합 6줄 합쳐 188B(0.8%) — 사실상 무효"* 라는 상수가 있었고 **그것도
철회됐다.** 그 0.8%는 ***줄 병합*** 을 잰 숫자인데 ***산문 전체*** 에 대한 주장으로 읽혀,
유효한 선택지를 지웠다. ⇒ **"안 되더라" 를 적을 때는 무엇을 잰 숫자인지 함께 적어라.**

**③ 초과 시 지시는 "압축" 이 아니라 "구조 변경" 이다.**

압축은 **이벤트**고 성장은 **프로세스**다 — 2026-08-08 에 1KB 를 확보했는데 같은 날 오후
한 세션이 도로 먹었다. 초과가 잡히면 아래 순서로 지시한다:

1. **완료분 → `ARCHIVE.md`**
2. **절차·플레이북·외부참조 → `PLAYBOOKS.md`** (lazy-load)
3. 1·2 로도 안 되면 **형제 항목 통합(−12 실측)** 또는 임계 재논의를 사용자에게 묻는다. 🔴 통합은 함정 포인터를 줄이는 일이라 **소유자 결정**이고, 임계 140 은 하네스가 준 값이라 «현재값에 맞추는» 변경은 금지다.**
   조용히 더 깎지 않는다 — 라벨은 회수(recall)를 담고 있어 그때부터는 압축이 곧 손실이다.

🔴 **금지 — 이건 개선이 아니라 사고다**

- **함정(§A2 측정·검증 규율 · §B 함정/해저드)을 lazy-load 로 내리지 말 것.**
  안 로드된 함정은 **다시 밟는다.** 내려도 되는 것은 *절차·전략* 뿐이다.
- **항목 삭제 금지.** 옮기는 것이지 지우는 것이 아니다.
- **승격은 복사가 아니라 이동이다.** 함정을 §A2/§B 로 올릴 때 `PLAYBOOKS.md` 의 원본을
  남기면 두 사본이 갈라진다 — 실제로 2026-08-14 승격이 그렇게 끝나 포인터 7개가 양쪽에
  살았고, `MEMORY.md` 가 가드설계에 축을 하나 더하는 동안 사본은 옛 4요소인 채였다
  (2026-08-23 감사에서 제거). **양쪽에 있는 사실은 한쪽만 고쳐진다.**

**④ 유효성 술어 — 옮기기 전후 포인터 집합이 같아야 한다.**

```bash
PTR='\]\([a-zA-Z0-9_.-]+\.md\)'          # ① 과 같은 정규식이어야 한다
# 이동 전
cat MEMORY.md PLAYBOOKS.md ARCHIVE.md | grep -oE "$PTR" | sort -u > /tmp/before.txt
# ... 이동 ...
cat MEMORY.md PLAYBOOKS.md ARCHIVE.md | grep -oE "$PTR" | sort -u > /tmp/after.txt
comm -23 /tmp/before.txt /tmp/after.txt   # 비어야 한다 = 손실 0
comm -13 /tmp/before.txt /tmp/after.txt   # 비어야 한다 = 유령 유입 0
```

🔴 이 술어 없이 섹션을 통째로 옮기면 **한 줄 흘려도 모른다.**
🔴 **양방향을 다 봐라** — `comm -23` 만 보면 실수로 *늘어난* 포인터를 못 잡는다.
🔴 **정규식이 ① 과 달라지면 이 술어는 무의미하다.** 좁은 정규식은 양쪽에서 똑같이
놓치므로 **차집합이 비어도 통과가 아니라 판정 불가**다.
🔴 덮어쓰기는 **임시파일 + rename** (truncate-then-fail 이 인덱스를 0바이트로 만든 적 있다).

**⑤ 참고 — `*_detail_*` / `*_history_*` 파일이 인덱스에 없는 것은 정상이다.**
부모 메모리가 `[[wikilink]]` 로 가리키는 분할본이다. 인덱스 링크(`](x.md)`)만 세면
"고아" 로 오판한다 — 고아 판정 전에 `[[x]]` 형태도 함께 세라.

검사 결과를 아래 형식으로 출력한다. `--dry-run` 플래그가 있으면 여기서 종료한다.

```
## Memory Audit Report  (YYYY-MM-DD)

### 1. Stale
- [file.md] 설명 — 권장 조치

### 2. 모순/불일치

### 4. CLAUDE.md 중복

### 5. 공통 규칙 후보
- [file.md] 승격 대상 규칙 요약 — 승격 위치 제안

### 6. 인덱스 예산
🔴 **모든 숫자는 자기가 무엇을 잰 것인지 이름을 달고 나온다.** 축마다 한 줄씩, 축을 합치지 않는다.
- MEMORY.md ① 문자: N자 / 문자 한도 24,986 — 여유 R자 (X%) → WITHIN / OVER
- MEMORY.md ② 줄 수: L줄 / 140줄 미만 → 미발화 / 발화  ← 🔵 리포 훅의 판정축(TASK-MONO-596)
  참고(판정 아님): 훅ptr P (**훅과 같은 정규식** `[a-z0-9_]+`) — 🔴 **정원은 더 이상 없다**
- MEMORY.md ③ 줄 수: L줄 / 140줄 미만 요구 → 미발화 / 발화
  🔴 **이 커맨드는 ③ 을 못 끈다** — 하네스 판정이라 여기서 «PASS» 여도 경고는 남을 수 있다
- 참고(판정 아님): 총 포인터 A개(넓은 정규식, 고유 U) · 바이트 B — 🔴 **어느 판정에도 안 쓰인다**
- 포인터 경로 C자 (Y%) — 압축 불가 / 산문 잔량 (N−C)자
- PLAYBOOKS.md: N자 / L줄 / 훅ptr P   ·   ARCHIVE.md: N자 / L줄 / 훅ptr P
- 🔵 **세 판정이 어긋나는 것은 정상이다** — 같은 방향을 가리킬 이유가 없다. 어긋났다고
  숫자를 의심하지 말고, **어느 축이 무엇을 재는지**(§2-6 ①)를 먼저 읽어라.
- (어느 축이든 발화인 경우) 구조 변경 후보: <절차성 섹션과 그 포인터 수>
  🔴 함정 섹션(§A2·§B)은 후보에서 제외했음을 명시
  🔴 **처방은 축을 보고 정한다** — ①만 넘었으면 산문 압축이 듣지만, ②③ 은 **항목 수**를
```

### Phase 4: 수정 실행

`--dry-run` 이 없으면 보고서를 출력한 뒤 **사용자에게 확인**을 받고 아래를 수행한다.

| 문제 유형 | 조치 |
|---|---|
| Stale | 메모리 파일 내용 업데이트 (날짜·상태·경로 수정) |
| 모순 | 낮은 우선순위 파일 수정, 내용 통일 |
| 댕글링 참조 (인덱스 링크) | `MEMORY.md` 에서 해당 항목 제거 |
| 댕글링 참조 (본문 경로) | 경로 수정 또는 관련 설명 삭제 |
| CLAUDE.md 중복 | 메모리 파일 삭제 + `MEMORY.md` 인덱스 항목 제거 |
| 공통 규칙 후보 | 사용자와 승격 여부 합의 후, 합의 시 CLAUDE.md 해당 섹션에 추가 + 메모리 삭제 |
| 인덱스 예산 초과 | 2-6 ③ 순서대로 **이동**(완료분→ARCHIVE, 절차→PLAYBOOKS). 🔴 압축·삭제·함정 강등 금지. 이동 후 2-6 ④ 포인터 집합 동등성 검사 필수 |

수정 후 `MEMORY.md` 인덱스가 실제 파일 목록과 일치하는지 재확인한다.

## Rules

- 보고서를 먼저 출력한 다음 사용자 확인을 받고 수정한다 (`--dry-run` 없는 경우).
- 한 번에 여러 문제를 발견해도 보고서는 한 번만 출력한다.
- 메모리 파일 삭제 전 반드시 내용을 읽어 확인한다.
- 공통 규칙 승격은 사용자가 명시적으로 동의한 경우에만 수행한다.
- 판단이 모호한 항목은 보고서에 `[?]` 표시 후 사용자에게 판단을 요청한다.
- 검사는 읽기 전용으로 시작하고, 수정은 Phase 4에서만 수행한다.
